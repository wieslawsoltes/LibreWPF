# ProGPU WPF Managed Subsystem Bring-up

## Porting Decision

For this port, "port" means reusing as much upstream managed WPF code as possible wherever it can compile and execute. ProGPU and Silk.NET are platform/rendering replacements at the boundary, not a reason to rewrite `System.Xaml`, `PresentationBuildTasks`, `PresentationCore`, `PresentationFramework`, controls, themes, resources, or the XAML compiler in the ProGPU bridge. New porting slices should first preserve the real managed subsystem path, then add the smallest native adapter or ProGPU primitive needed at the platform/render boundary.

The current architecture keeps this boundary:

- `System.Xaml` remains the real WPF XAML reader, schema, object writer, and markup-extension implementation.
- `PresentationBuildTasks` remains the real WPF XAML/BAML compiler path (`MarkupCompilePass1`, `MarkupCompilePass2`, `MarkupCompiler`, BAML writer/records).
- `PresentationFramework` remains the real WPF application, window, resource, style/template, control, document, and BAML/XAML loader implementation.
- `PresentationUI` remains the real WPF document/application support assembly. Windows builds keep the native `System.Printing` C++/CLI implementation, while non-Windows bring-up uses the existing `System.Printing-ref` project so the managed theme/XAML graph can compile without Visual C++ targets.
- Theme assemblies remain real WPF theme projects with `Page` XAML and internal markup compilation.
- `ProGPU.Wpf` supplies adapter services for rendering, retained scene ownership, portable windowing, input, dispatcher wakeups, and platform services without adding ProGPU references to the managed WPF subsystem projects.

## Basic App Smoke Ladder

1. **Managed core build gate**
   - Build `WindowsBase`, `System.Xaml`, `PresentationCore`, `PresentationFramework`, `PresentationUI`, `PresentationBuildTasks`, and at least one theme assembly.
   - Purpose: prove the upstream managed subsystem graph remains reusable on non-Windows.

2. **Code-only app gate**
   - Instantiate `Application`, `Window`, layout controls, text controls, resource dictionaries, and drawing visuals without XAML.
   - Route `Window.Show` through `PortableWindowActivationService` into the ProGPU/Silk.NET host.

3. **XAML compiler gate**
   - Build a tiny app with `ApplicationDefinition` and `Page` items using the real `PresentationBuildTasks`.
   - Verify generated BAML and code-behind connector paths are produced by WPF's compiler, not a ProGPU-local compiler.

4. **XAML runtime gate**
   - Load the generated app resources through real `PresentationFramework` BAML/XAML loaders.
   - Verify `ResourceDictionary`, `Style`, `ControlTemplate`, `VisualStateManager`, `StaticResource`, `x:Shared`, `DynamicResource`, and namescope behavior.

5. **Application run gate**
   - Call real `Application.Run()` on the compiled XAML app.
   - Verify WPF's own `StartupUri`, startup dispatcher work, root `Window.Show`, portable activation, run-loop handoff, shutdown, close, and dispose ordering without replacing managed app lifetime code.

6. **Theme gate**
   - Compile and load the Fluent theme project and representative style dictionaries (`Button`, `Window`, `TextBox`, `RichTextBox`).
   - Verify themed controls render through the ProGPU retained scene bridge.

7. **Rich framework gate**
   - Exercise controls, routed input/commands, input bindings, focus, selection, `TextBox`, `RichTextBox`, `FlowDocument`, bindings, resources, and templates.
   - Keep failures attached to the real WPF subsystem that produced them instead of replacing the subsystem.

8. **Rendering integration gate**
   - Continue lowering WPF drawing, effects, brushes, text, 3D, retained invalidation, and dirty-branch replay to native ProGPU primitives.
   - Managed WPF should own semantics; ProGPU should own GPU execution.

## SDK Deliverable Target

The product target is a custom SDK-style distribution, not a source-edit migration. A WPF app should be able to move to the ProGPU/Silk.NET platform by changing only the project SDK, for example from `Microsoft.NET.Sdk.WindowsDesktop` to the ProGPU WPF SDK package/name used by this port. The SDK must import the WPF markup compiler targets, redirect framework references to the ported managed WPF assemblies, bring in the ProGPU/Silk.NET runtime assets, select the portable window/rendering platform, and keep existing `App.xaml`, `Page`, `Resource`, `ApplicationDefinition`, references, generated BAML, and code-behind behavior intact. Any required app-code changes are treated as portability bugs unless the original application depends on explicitly Windows-only interop.

This SDK target depends on the same reuse boundary as the port itself: keep `System.Xaml`, `PresentationBuildTasks`, `PresentationCore`, `PresentationFramework`, controls, resources, styles/templates, themes, and XAML/BAML managers on WPF code paths, and package only the platform/rendering substitutions behind MSBuild properties, assembly references, runtime identifiers, and native assets.

Latest SDK deliverable hardening now treats stale mutable package output as a portability risk. The SDK CI removes each local `11.0.0-dev` ProGPU, WPF transport, ProGPU bridge, and SDK package before packing, then rebuilds the package-mode smoke from the refreshed local feed. This keeps the no-source-change SDK lane from validating or launching stale `ProGPU.Scene`, `ProGPU.Wpf`, or WPF transport assemblies that can otherwise reproduce the Retina upper-left-quadrant smoke-window failure even after the source render path is fixed.

The first package skeleton now lives under `packaging/ProGPU.Wpf.Sdk`. It produces an MSBuild SDK package layout with `Sdk/Sdk.props`, `Sdk/Sdk.targets`, and `targets/ProGPU.Wpf.Sdk.*`; it layers on the existing WindowsDesktop SDK so WPF markup compilation remains the real `PresentationBuildTasks` path, keeps the base SDK's `UseWPF` framework-reference path disabled in portable mode, declares Silk.NET/ProGPU platform properties, removes WindowsDesktop targeting-pack package downloads, and provides package-reference plus local-artifact extension points for the ported WPF and ProGPU assemblies. The package now packs as an `MSBuildSdk` nupkg with verified root readme, `Sdk/`, and `targets/` contents. Package mode now references the ported managed WPF bundle through `ProGpuWpfManagedPackageId`/`ProGpuWpfManagedPackageVersion`, keeps dependency versions aligned to the SDK package version, and expects the WPF transport bundle to own real WPF assembly identities with both `ref/net10.0` and `lib/net10.0` payloads while `ProGPU.Wpf` keeps its shim `PresentationCore` compile reference private and advertises only its ProGPU/Silk runtime dependencies. Local-artifact mode remains the source-built validation path. `src/ProGPU.Wpf.SdkSwitchSmoke` validates the SDK-switch path with only `Sdk="ProGPU.Wpf.Sdk/11.0.0-dev"` in the project file, normal default `App.xaml`/`Page`/code-behind item discovery, portable `net10.0`, default assembly name/root namespace, and package mode by default; local artifact roots are now opt-in rather than part of the smoke project's normal build contract. The SDK now owns the portable markup-compiler defaults for `InternalMarkupCompilation=true` and `AlwaysCompileMarkupFilesInSeparateDomain=false`, so the SDK-switch app no longer carries those PresentationBuildTasks compatibility properties itself. The SDK now leaves runtime patch selection to the active .NET SDK by default while keeping `ProGpuWpfRuntimeFrameworkVersion` as an opt-in override hook, so the smoke app no longer pins `RuntimeFrameworkVersion`. The smoke app now exercises a compiled merged resource dictionary, dynamic/static resources, explicit styles, `DataTemplate`, collection binding, selected-item `ElementName` binding, generated `Button.Click` code-behind hookup, compiled `CommandBinding`, compiled `KeyBinding`, routed command execution through `Button.Command`, `TextBox` binding, and `RichTextBox`/`FlowDocument` object creation while still requiring no app-specific ProGPU project properties. The SDK now also brings in WPF support packages (`System.IO.Packaging`, `System.Windows.Extensions`, `System.Configuration.ConfigurationManager`, and `System.Formats.Nrbf`), brings in the Silk.NET managed/native package closure, defaults to the current runtime identifier while keeping the output path stable, copies resolved managed and native package runtime assets, copies the fuller local WPF runtime set including UIAutomation, primitives, manipulation, and theme assemblies when those artifacts are present, and injects an SDK-owned module initializer that registers the existing ProGPU portable activation boundary on non-Windows. `src/ProGPU.Wpf.SdkSwitchRuntimeHarness` is now the external runtime check for that SDK-produced app: it is a plain `Microsoft.NET.Sdk` console loader that consumes the compiled smoke app output, verifies WPF/ProGPU/Silk.NET/support-package managed assets plus current-platform WebGPU/GLFW native assets are present beside the app, verifies SDK auto-bootstrap registration, invokes generated `App.InitializeComponent()`, validates `StartupUri`, richer BAML-created application resources and `MainWindow` object graphs, namescope lookup, binding, generated events, command/input binding metadata and routed command execution, templating, collection and rich-document objects, SDK-loaded portable `MessageBox.Show(...)`, `Clipboard`, `OpenFileDialog`, `SaveFileDialog`, `OpenFolderDialog`, and representative `SystemParameters` public API/resource-key behavior, then runs the same SDK-built app through real `Application.Run()` with WPF's `PortableWindowActivationService`, `PortablePresentationSource`, dispatcher flushes, `PortableMediaContextRenderService`, owner-window MessageBox callbacks, and owner-window file/folder dialog callbacks without creating a native Silk.NET window.

The SDK/package path must not depend on ProGPU shim-only WPF API additions when real WPF assemblies are loaded. Retained WPF replay and object render-data replay now use native `ProGPU.Scene.DrawingContext` command sinks directly; the flat shim `DrawingContext` is left only for explicit transition `Draw` callbacks. This preserves the managed WPF assembly identity supplied by the transport package and keeps ProGPU-specific rendering state behind the SDK/bridge boundary.

The native host boundary also owns early DPI synchronization. The ProGPU/Silk.NET host resolves logical WPF client dimensions and physical framebuffer dimensions during native load and resize, caches that `RenderSurfaceGeometry`, and pushes the resulting DPI scale into WPF's `PortablePresentationSource` before rendering. WPF manager, layout, and XAML/runtime code continue to observe DIP-sized windows while ProGPU owns the Retina/HiDPI physical swapchain. When the monitor-service path still reports `1.0` on macOS, the host reads the native Cocoa window screen's `backingScaleFactor` before the first frame and preserves cached WPF DIPs when Silk.NET reports native dimensions that already look scaled. If startup native/requested/declared caches are all polluted with physical dimensions, the host reconciles the resolved client size against the arranged WPF root `RenderSize` only when the resolved value equals the physical framebuffer, so SDK-switched apps do not render into only the upper-left physical quadrant while real logical resizes still update WPF layout.
