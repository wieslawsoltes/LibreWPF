# ProGPU WPF Port Architecture

## Porting Definition

Porting means reusing all upstream WPF managed code possible wherever it can reasonably compile and execute: dependency properties, dispatcher/app lifetime, controls, layout, resource lookup, styles/templates, routed input/commands, text objects, XAML/BAML compilation, and theme dictionaries remain WPF-owned. ProGPU and Silk.NET replace the Windows-native rendering, composition, windowing, input, and local OS service boundaries. New work should first try to keep the original WPF managed subsystem on the active path, then add native ProGPU APIs only where the old MIL/DWrite/WIC/Win32/D3D boundary cannot be made portable or where performance-critical GPU execution belongs in ProGPU. Bridge-local compatibility code is temporary unless it preserves a source-level WPF manager path or isolates a native seam for later ProGPU ownership.

The delivery shape should be a custom MSBuild SDK for existing WPF applications. The target user action is a project SDK change, with no source-code changes for normal WPF apps: the SDK imports WPF markup compilation, selects the ProGPU/Silk.NET platform, supplies the ported managed WPF assemblies and native ProGPU assets, and preserves existing `ApplicationDefinition`, `Page`, `Resource`, generated BAML, resource lookup, themes, and code-behind behavior. Existing WPF project markers such as `OutputType=WinExe` and `UseWPF=true` should remain in app projects; the ProGPU SDK treats `UseWPF=true` as the app's WPF markup intent, then hides the base WindowsDesktop framework-reference path internally so restore/build resolves the portable WPF transport and ProGPU/Silk.NET package graph. Any extra app-code requirement should be treated as a compatibility issue or explicitly documented Windows-only interop exception.

The SDK-only migration contract is now an acceptance gate, not just a packaging preference. Each porting slice should preserve the original managed WPF manager path whenever possible, prove that path through SDK-produced output, and classify any required application source edit as either a bug in the portable WPF transport or a deliberate Windows-only interop exception. ProGPU/Silk.NET should own native rendering, shaders, composition surfaces, OS windows, input intake, and local OS services; it should not replace WPF resource, binding, style, template, layout, command, document, XAML, or application-lifetime managers unless the original code cannot be made portable.

Package-mode freshness is part of the architecture, not just test hygiene. The SDK switch runtime harness and generated external SDK smoke now byte-match required `Microsoft.DotNet.Wpf.GitHub` WPF transport assemblies from local packages and app output against available repository-built WPF assemblies, alongside the existing ProGPU bridge/compositor package checks. This closes the stale mutable-package path where the render backend is current but an older `PresentationCore` or `PresentationFramework` still constrains WPF layout or presentation-source state, producing upper-left/offset window content even though source-level HiDPI pixel tests pass.

The SDK render-offset boundary is guarded at three levels. Package-mode freshness checks reject stale WPF and ProGPU assemblies before runtime validation, headless retained-layer pixel checks prove a full `420x840` DIP WPF rectangle reaches an `840x1680` physical render target, and packaged host startup-resize checks prove the shipped Silk.NET/ProGPU host keeps WPF logical client dimensions after a Retina native resize. WPF remains responsible for managed layout and client-size state; ProGPU/Silk.NET owns physical framebuffer size, DPI scale, viewport placement, and retained-layer placement.

Input-driven rendering and native resize layout now use the same ownership split. WPF input, focus, command, binding, and control managers remain responsible for mutating managed state, while `ProGpuWpfWindowHost` wakes the native Silk.NET loop whenever WPF requests a render from input or presentation-source callbacks. Frame coalescing includes WPF logical size and DPI scale, so resize or display-scale changes cannot be skipped only because the physical framebuffer dimensions are unchanged. Portable `Window.ArrangeOverride` trusts the logical arrange bounds supplied by `PortablePresentationSource`, keeping native resize content sizing in WPF layout instead of freezing content to the original XAML `Width`/`Height` after the Silk.NET window changes size.

Portable hit testing should consume ProGPU render-time cache data instead of rebuilding WPF drawing content on the CPU once a frame has produced a GPU cache. The compositor builds a GPU-resident quadtree plus precise primitive/path-segment records while it is already processing render commands, strokes, fills, transforms, opacity, and clips; helper data such as line-stroke direction/segment length and ellipse center/inverse-radii is computed at primitive-cache build time and uploaded with the hit-test primitive buffer for reuse by point and region shaders. Render-command cache tests now assert `DrawLine` and `DrawEllipse` produce those helper payloads directly from the rendering pass. Path helper data follows the same rule: `CompilePathCommand(...)` warms the shared `PathAtlas` hit-test path cache during render lowering for fill and stroke paths, and draw commands are added to the hit-test index after render compilation while clip/opacity state remains ordered before drawing; the hit-test builder then consumes the already prepared `GpuPathRecord`/`GpuPathSegment` payloads instead of compiling the same WPF path again. Visual-level clips, including WPF layout `ClipBounds` and outer `ScrollableAreaClip` viewports, are pushed into the same cache stack as render clips so scrolled Xceed/DataGrid content cannot hit outside its rendered viewport. Offscreen layer/effect passes suspend hit-test cache writes, then cached layer/effect texture replays add owner-bound GPU primitives on the main pass through the visual `HitTestId`; normal uncached geometry still contributes precise primitive/path metadata from render-command compilation. Portable mouse input, direct `UIElement.InputHitTest(...)` callers, the public topmost point helper, point callback hit testing, and geometry-region callback hit testing now query that cache through `GpuHitTestEngine` and resolve results back to retained WPF source owners; cache misses are handled as misses instead of falling through to CPU media hit testing after a valid frame exists. Ordered GPU list queries remain caller-bounded, but their summary now reports the raw matched primitive count before capacity truncation so large visual trees can detect overflow without rerunning WPF drawing-content hit tests; ProGPU stores those native results as a distinct-by-id z-ordered list that keeps the highest-z primitive for each id, and the WPF composition target resolves the resulting distinct records directly to retained owners before using the overflow signal to retry internally when unmapped top hits or native capacity limits leave the requested owner/candidate span underfilled. Direct input-hit-test calls still use WPF's raw/enabled promotion and input visibility semantics after ProGPU supplies the ordered owner list. Filtered point and geometry callbacks apply WPF's `HitTestFilterBehavior` over the GPU-resolved owner ancestor path before invoking user result callbacks, so arbitrary user delegates remain in PresentationCore while drawing-content geometry stays on the render cache. Paths that cannot be compiled into precise GPU path segments must fail closed rather than becoming broad bounds boxes. Geometry-region callbacks currently use the GPU bounds-query mode with shader-classified detail for safe axis-aligned bounds/rect cases; axis-aligned rounded-rectangle fill/stroke, ellipse fill/stroke, and cached line-stroke candidates now reuse cached primitive metadata to reject empty rectangular-region hits such as rounded corners, stroke holes, ellipse corners, line broad-bounds misses, and flat-cap overhangs, while cached path fill/stroke candidates test rectangular query regions against the same path segment buffer used for point-precise path hits. The first non-rectangular query mode is wired into the WPF bridge: `GeometryHitTestParameters` preserves a cheap axis-aligned ellipse hint, `PortablePresentationSource` routes those query bounds through `TryQueryEllipseAll(...)` when the reference-to-root transform keeps the query axis-aligned, and ProGPU culls against the actual ellipse region before resolving WPF owners. Cached ellipse fill/stroke, line-stroke, and path fill/stroke primitives now also participate in that ellipse-region mode: the shader rejects proven separated ellipse pairs from cached center/radii data, rejects line broad-bounds false positives from cached direction/length data, rejects path fill holes and path-stroke broad-bounds false positives from cached path segments, reports same-center containment when radii ordering proves it, and rejects same-center ellipse-stroke hole hits. Exact arbitrary non-rectangular region-vs-fill/stroke/path precision remains backend work, not a reason to reintroduce managed WPF geometry replay.

Portable point and input hit-test callback plumbing should stay caller-buffer based. ProGPU `main` exposes `PortableHitTestAllBufferOverride` from its WPF shim interface, source-built `PresentationCore` exposes the same delegate beside the legacy array callback, and `WpfPortablePresentationSourceBridge` installs both while serving the buffer callback from `ProGpuWpfWindowHost.TryHitTestOwners(..., Span<object?>, ...)` with in-place transparent-overlay filtering. Source-built `PortablePresentationSource` rents a small owner buffer through `ArrayPool<object>` for point callback hit testing and `UIElement.InputHitTest(...)`, returning it after WPF has applied filter/input visibility semantics. The array-returning callbacks remain for compatibility and geometry-region candidate arrays, but hot pointer/input paths should not require host-created owner arrays.

Retained rendering must also observe WPF-owned visual state that changes without public collection or property-change notifications. ScrollViewer viewport movement stays in managed WPF layout and `Visual` state; ProGPU should not duplicate scroll policy, but the retained invalidation tracker must snapshot low-level visual offset, internal visual clip, scrollable-area clip, clip/transform references, opacity, and render size so hidden WPF mutations mark the relevant retained branch dirty. WPF's public `UIElement.Clip` is not the full rendered clip after layout: `UIElement.ensureClip(...)` writes layout viewport clips, including `ScrollContentPresenter.GetLayoutClip(...)`, into protected `Visual.VisualClip`. The bridge therefore reads `VisualClip` first and falls back to public `Clip` for pre-layout or shim objects. WPF `VisualClip`/`Clip` is local visual state, while `VisualScrollableAreaClip` is an outer-space viewport clip applied after visual transform/offset; ProGPU therefore carries it separately as `OuterClipBounds` and applies it through the parent transform so scrolled content moves under a stable viewport. This is the current transition bridge for Xceed Toolkit scrolling and AvalonDock content surfaces until source-level managed WPF traversal can publish exact visual dirty records directly.

`DrawingVisual` and `UIElement` retained content follow the same source-integrated rule. Source-built WPF now exposes existing drawing content through `IPortableDrawingContentSource`, letting ProGPU reach retained `RenderData` without reading the private `_content` or `_drawingContent` fields for normal visual content. Source-built `RenderData` then publishes its active instruction bytes and dependent resources through `IPortableRenderDataSource`, so retained replay no longer reflects `_buffer`, `_curOffset`, or `_dependentResources` on the normal path. The retained invalidation tracker follows those same typed drawing-content and render-data seams before private-field traversal, so normal retained content dependencies can dirty the owning branch without probing `_content`, `_drawingContent`, or render-data resource fields. Source-built `Visual` also exposes child traversal through `IPortableVisualChildrenSource` and core visual state through `IPortableVisualStateSource`, so normal subtree replay no longer reflects protected `VisualChildrenCount`, `GetVisualChild(int)`, `VisualOffset`, `VisualTransform`, `VisualClip`, `VisualScrollableAreaClip`, `VisualOpacity`, or `VisualOpacityMask`. Source-built `UIElement` exposes arranged render size and `ClipToBounds` through `IPortableVisualLayoutStateSource`, while `FrameworkElement` extends the same state with its computed `GetLayoutClipInternal()` result. Normal retained owner bounds, opacity-mask bounds, clip-to-bounds rectangles, layout clips, retained layout-state invalidation, and host root render-size/client-size reconciliation now use the typed seam before falling back to transition probes. The private-field/member bridge remains transitional only for compatibility fakes and non-source-integrated shapes while the remaining retained resource/effect/cache extraction seams are moved behind typed contracts.

Third-party WPF interop compatibility is handled as a public API facade, not as a rendering/windowing backend. `PortablePresentationSource` can expose a synthetic `HwndSource` with a stable handle for `PresentationSource.FromVisual(...)`, `PresentationSource.FromDependencyObject(...)`, `HwndSource.FromHwnd(...)`, and `HwndSourceHook` callers such as AvalonDock floating-window controls. WPF internal source lookup keeps using `CriticalFromVisual(...)` so input providers, root visual ownership, layout invalidation, render scheduling, and dispatcher work remain attached to the portable ProGPU/Silk.NET source. The facade delegates root visual and input-provider access back to the portable source, portable coordinate conversion no-ops before Windows-only native calls, and access-key scope comparisons normalize the facade back to the owner source.

Third-party popup and dropdown editors follow the same ownership rule. Xceed `CheckComboBox`, `ColorPicker`, `CalculatorUpDown`, `DropDownButton`, and `SplitButton` should use their normal WPF templates, bindings, popup roots, and command handlers in SDK-switched apps. The portable layer must make `PresentationSource.FromVisual(...)` and popup-root composition usable for those controls without adding app-side ProGPU APIs; real native z-order, monitor placement, capture, and accessibility parity remain ProGPU/Silk.NET platform-service work rather than a reason to fork Xceed or WPF popup manager code.

Third-party input, selector, and range editors should likewise stay on WPF manager paths. Xceed `AutoSelectTextBox`, `WatermarkPasswordBox`, `MaskedTextBox`, `TimePicker`, `DateTimeUpDown`, `TimeSpanUpDown`, `ByteUpDown`, `DoubleUpDown`, `LongUpDown`, `DecimalUpDown`, `ColorCanvas`, `MultiLineTextEditor`, `ButtonSpinner`, `CheckListBox`, `WatermarkComboBox`, `RangeSlider`, and `RichTextBox` should compile from ordinary XAML, use Toolkit templates and dependency properties where the Toolkit exposes them, and update normal WPF bindings/collections. `WatermarkPasswordBox.Password` is state-only in the Xceed 5.1.2 free package and is therefore validated as control state rather than as a binding contract. ProGPU/Silk.NET input delivery may need to scroll targets into view and normalize native pointer/text events, but auto-select behavior, mask parsing, date/time up-down coercion, numeric value coercion, color-canvas state, spinner events, selected-item collections, range coercion, rich-text formatting adapters, and value coercion remain managed Toolkit/WPF behavior.

Multiple portable WPF windows can share managed WPF image objects but must not share GPU texture views across WebGPU devices or surfaces. `WpfBitmapSourceImageAdapter` therefore caches adapted WPF bitmap textures per `WgpuContext`, and ProGPU's compositor validates texture commands against the active context before creating bind groups. This keeps AvalonDock floating windows and future WPF popups/owned windows from crashing the native backend when the same icon, bitmap, or brush source appears in more than one native Silk.NET window.

The native host can use local OS display-scale APIs when the cross-platform window stack reports insufficient DPI data. `ProGPU.Backend.DisplayScaleResolver` is the reusable ProGPU/Silk.NET boundary for this: it normalizes monitor scale values, keeps valid Silk/monitor scale values authoritative, and on macOS accepts Cocoa native handles shaped as either `NSWindow` or `NSView`. It reads an object's own `backingScaleFactor` when available, otherwise probes `screen` or `window.screen`, and uses `NSScreen.mainScreen` only when the native handle cannot supply a screen. `ProGpuWpfWindowHost` delegates to this backend service so the SDK migration contract stays source-free and future WPF, WinUI-shim, and ProGPU-hosted controls share one display-scale boundary instead of carrying AppKit P/Invokes in each host.

Portable WPF platform services use typed interop registries rather than reflected service discovery. Source-built `PresentationCore` now publishes its portable clipboard and `MediaContext` render-wakeup registrations through `ProGPU.Wpf.Interop.PortableWpfServiceRegistry` at module load, and source-built `PresentationFramework` publishes window activation, main-window query, window close/cancel, input, input dispatcher marshaling, dispatcher flush, activation-state, drag/drop, launcher, message-box, and file-dialog registrations the same way. `ProGPU.Wpf` registers and invokes the host callbacks through `IPortableClipboardServiceRegistrar`, `IPortableMediaContextRenderServiceRegistrar`, `IPortableWindowActivationServiceRegistrar`, `IPortableLauncherServiceRegistrar`, `IPortableMessageBoxServiceRegistrar`, and `IPortableFileDialogServiceRegistrar`. New platform hooks should follow the same signed interop-service pattern and fail closed if the loaded WPF assembly does not publish the typed registrar.

Referenced WPF libraries are part of the same SDK contract. The SDK bootstrap source is executable-only (`Exe`/`WinExe`) so class libraries compiled with the ProGPU WPF SDK do not register or overwrite app-level portable window services when their controls are loaded. The SDK target carries the ProGPU render/runtime closure explicitly, including `ProGPU.Compute` and `ProGPU.Transpiler`, so both package mode and local-artifact mode can produce a complete `deps.json` for the ProGPU scene stack. The current source-tree smoke lane now uses package mode by default against the `Microsoft.DotNet.Wpf.GitHub` transport package, with local artifact roots remaining an explicit source-build escape hatch. The transport package pack validates that required WPF `lib/net10.0` and `ref/net10.0` payloads are present before NuGet packaging, preventing metadata-only SDK transport packages from satisfying restore while failing at runtime.

Theme assemblies are transport payloads, not ProGPU-side theme reimplementations. `Microsoft.DotNet.Wpf.GitHub` must carry the full managed WPF theme set (`PresentationFramework.Aero`, `Aero2`, `AeroLite`, `Classic`, `Fluent`, `Luna`, and `Royale`) in both `lib/net10.0` and `ref/net10.0`, and the SDK must copy/validate those same assemblies in package mode and local-artifact mode. This keeps WPF theme probing, `ThemeInfo`, default style lookup, and compiled theme dictionaries on the managed WPF path for SDK-switched apps, while ProGPU/Silk.NET renders the resolved style/template visual tree. The Fluent ref project uses the real `PresentationFramework.Fluent` assembly identity so the transport package does not ship a mismatched `Fluent.dll` ref asset.

Optional managed WPF framework assemblies are transport payloads too. `System.Windows.Controls.Ribbon` is built from the real WPF source project, including its compiled Ribbon theme dictionaries and reference assembly, and is shipped through the same `Microsoft.DotNet.Wpf.GitHub` `lib/net10.0` plus `ref/net10.0` package path. SDK-switched apps should be able to use Ribbon XAML by changing the project SDK only; Ribbon control state, command routing, namescope lookup, and theme/resource probing remain WPF-owned, while ProGPU/Silk.NET receives the resolved control/template visual tree. The current package-mode smoke validates a collapsed Ribbon object graph because visible Ribbon templates measure `RibbonTwoLineText` through WPF's full LineServices formatter; visible Ribbon rendering belongs to the broader ProGPU/cross-platform text-formatting replacement, not to SDK package wiring.

The SDK contract must be proven outside the repository build graph. `src/ProGPU.Wpf.SdkExternalSmokeHarness` creates a temporary app/library pair outside the repo root and builds it from packages without generated repo props or local artifact-root properties. That harness is the compatibility gate for the intended migration surface: the generated app project keeps only normal WPF project metadata after switching `Project Sdk`, while NuGet package source configuration remains an environment/feed concern rather than an app code or project-property requirement. Referenced-library theme lookup is part of that gate: the external library now contributes `ThemeInfo`, `Themes/Generic.xaml`, a `DefaultStyleKey` custom control, and a component-resource-keyed brush, and the generated app validates the resulting default template from compiled output plus `XamlWriter.Save(...)`/`XamlReader.Parse(...)` round-tripping of that loaded theme template. Third-party package restore is also part of the gate: the same generated app now references `Extended.Wpf.Toolkit` like a normal WPF app, validates Xceed `WatermarkTextBox`, numeric/color/calculator editors, `DropDownButton`/`SplitButton` popup state and routed actions through the portable public `HwndSource` facade, plus a simple AvalonDock layout using the package's Aero theme, and verifies the Xceed Toolkit/AvalonDock runtime assets and deps are copied to output. The generated default-item app also includes a source-free 100,000-row WPF `DataGrid` with explicit virtualization, recycling, pixel scrolling, a large `ScrollIntoView(...)` offset check, and realized-row bounds so SDK-switched apps exercise large tabular workloads outside the repo-local sample graph. ProGPU/Silk.NET should render the resolved control tree; WPF remains responsible for theme assembly probing, resource keys, template serialization, package XAML creation, data binding, collection views, popup control templates, and template application.

Build-time localization extraction is part of the external SDK gate, but it is separate from runtime localization metadata validation. The SDK harness keeps the main no-source-change app on normal compiled BAML so `Localization.GetComments(...)` and `Localization.GetAttributes(...)` remain attached at runtime, and builds a second package-only SDK project with `LocalizationDirectivesToLocFile=All` to validate WPF `PresentationBuildTasks` `.loc` generation for `x:Uid`, `Localization.Comments`, and `Localization.Attributes`. This matches WPF's behavior: the `All` directive emits localization directives to `.loc` output for localization tooling and should not be enabled on the runtime smoke app when that app is proving attached metadata retention.

Compiled page navigation is part of the same external SDK gate. The generated external app now contains default-item `Page` XAML files, a `Frame` that loads the initial page, reports WPF navigation events, navigates to a second compiled page, returns through the WPF journal, then goes forward through the same journal entry directly, through stock `NavigationCommands`, and through public `NavigationService` APIs, plus a compiled `NavigationWindow` that performs the same source/second/back/forward journal flow through a portable shown window and its `NavigationService`. ProGPU/Silk.NET should supply the native run-loop, input, windowing, and rendering surfaces around this; page loading, namescopes, navigation commands, navigation services, navigation-window behavior, navigation events, and journal state remain managed WPF responsibilities.

Application resources and data presentation are part of the external SDK gate as well. The generated app now merges `ExternalResources.xaml` through `App.xaml`, validates static and dynamic resources from `Application.Resources`, validates `x:Shared="False"` brush instance semantics through separate `StaticResource` consumers and repeated dictionary lookup, mutates a dynamic brush and observes existing element invalidation, loads a compiled `DataTemplate`, validates template binding over an `ExternalItem`, and verifies `ObservableCollection` changes propagate to a bound `ListBox`. ProGPU/Silk.NET should render the resulting visual/property state; it should not duplicate WPF resource dictionaries, shared/unshared resource policy, data templates, binding expressions, or collection-view behavior.

Binding manager behavior is part of the external SDK gate. The generated app now compiles value converter and multivalue converter resources, `MultiBinding`, `PriorityBinding`, `FallbackValue`, `TargetNullValue`, explicit two-way binding source updates, `SourceUpdated`/`TargetUpdated` transfer event handlers, `IDataErrorInfo`, `INotifyDataErrorInfo`, and a custom `ValidationRule`, then validates converter output, child binding metadata, priority fallback, fallback/null-value binding metadata, binding transfer-event metadata, data-error validation, notify-data-error invalidation, validation failure/recovery, and source update from SDK-built output. TextBox editing behavior is also part of that external SDK gate. The generated app now validates `TextChanged`, selected text, selection start/length, selected-text replacement, caret positioning, `AppendText(...)`, `IsUndoEnabled`/`UndoLimit` and empty undo/redo behavior for programmatic edits, validation failure/recovery, and explicit binding source updates from SDK-built output. Data-provider resources are part of the external SDK gate. The generated app now compiles `ObjectDataProvider` method invocation and `XmlDataProvider` inline `x:XData`/XPath resources from a project that only changes to the ProGPU WPF SDK, then validates provider metadata, generated data, and bindings that consume those provider resources. Managed imaging primitives are part of the external SDK gate. ## Current WPF Rendering Boundary

WPF managed rendering persists content in `RenderData`, `Drawing`, `DrawingVisual`, and `Visual` objects. Those objects are marshalled into `DUCE.Channel` command streams and consumed by MIL/native rendering. The Windows-only seams include:

- `DUCE.Channel`, `MILCMD`, and `MilCoreApi` P/Invoke calls.
- `HwndSource`/`HwndTarget` and Win32 message handling.
- D3D, WIC, DWrite, tablet, input, clipboard, drag/drop, and monitor/DPI APIs.

## ProGPU Replacement Boundary

ProGPU replaces MIL/D3D composition with:

- `ProGPU.Backend.WgpuContext` for WebGPU device, queue, surface, and swapchain management.
- `ProGPU.Scene.Compositor` for retained visual rendering.
- `ProGPU.Scene.DrawingContext` and `RenderCommand` for recorded drawing operations.
- Silk.NET windowing for cross-platform surface ownership and event pumping.

Transformed arcs are kept as native ProGPU `ArcSegment` values through `ProGPU.Vector.ArcSegmentGeometry.TryTransformArcSegment`, including translation, positive scale/rotation fast paths, arbitrary affine shear, and orientation-reversing transforms that flip sweep direction; only truly degenerate arcs fall back to endpoint lines. The ProGPU WPF/WinUI path API shims follow the same rule for parsed SVG/WPF arcs and geometry transforms, so API-level path arcs reach the native vector arc shader instead of being replaced by endpoint line placeholders. The ProGPU `PresentationCore` path shim now preserves original WPF path coordinates and stores `Geometry.Transform` on the native `DrawPath` command; the compositor and path atlas therefore own transformed-arc evaluation for both filled and stroked paths instead of relying on managed shim-side point baking. The same shim-level path conversion is used by `DrawingContext.PushClip(Geometry)`: path-compatible WPF clips record native `PushGeometryClip` commands with `Geometry.Transform` composed with the active drawing transform, so ProGPU's mask path handles non-rectangular clips and transformed arc clips instead of an axis-aligned bounds approximation. Primitive line, rectangle, rounded-rectangle, and ellipse commands apply active dynamic `GuidelineSet`, `PushGuidelineY1`, and `PushGuidelineY2` snapping before command recording when the current transform is axis-aligned; `PushGuidelineY2` preserves the driven-edge offset. WPF-shaped `LineJoin`, `MiterLimit`, and `PenLineCap` values are copied through the shim `Pen` into native ProGPU vector pens on recorded commands, with miter limits clamped to WPF's effective minimum of `1.0`. ProGPU vector path stroking now emits native filled triangle geometry for miter, bevel, and round joins between adjacent line, quadratic Bezier, cubic Bezier, and arc segments using endpoint tangents, falls back from miter to bevel when the miter limit is exceeded, suppresses hard join filler geometry when the incoming path segment carries `IsSmoothJoin`, emits native square, round, or triangle cap geometry for open line, quadratic Bezier, cubic Bezier, and arc paths using endpoint tangents, and emits valid arc strokes as fixed-quad `ArcSdf` primitives by creating reusable `ProGPU.Vector.ArcShaderParameters` for transformed ellipse center/axis vectors and passing that native arc ABI to vector WGSL for fragment-level nearest-ellipse and WPF/SVG sweep evaluation. The older segmented `ArcStrip` compositor/WGSL path has been removed, so valid arcs no longer have a strip-tessellation fallback. Positive and dot-style dash-array pens now delegate WPF dash-array normalization, odd-array duplication, dash-offset state, and dot-dash promotion to `ProGPU.Vector.DashPattern`; straight `DrawLine` calls and rectangle outlines replay as native line segment commands in local coordinates while preserving active transforms and continuous rectangle dash phase. Dashed path-compatible geometries keep WPF arc, quadratic Bezier, and cubic Bezier spans native by requesting visible dash intervals from `ProGPU.Vector.ArcSegmentGeometry.TryCreateDashedArcSegments(...)` and `ProGPU.Vector.BezierSegmentGeometry.TryCreateDashed*BezierSegments(...)`, then recording those spans as one-segment `DrawPath` commands; dash state advancement stays in ProGPU vector helpers, and rendering stays on the ProGPU arc/Bezier shaders instead of bridge-local line fallback geometry. Skia `SKPaint` dash path effects now map into the same native vector pen dash metadata, so Skia/WPF-compatible API users share backend-owned dash lowering rather than duplicating managed span emitters. Positive dash-array rounded-rectangle and ellipse outlines build ProGPU-owned primitive paths through `ProGPU.Vector.PrimitivePathGeometry`, so rounded corners and ellipse curves emit native arc dash commands instead of bridge-local polyline approximations; filled dashed primitives or geometries emit the fill before the segmented outline. Filled dashed combined geometries keep their native combined fill and emit operand-boundary dashed outline segments with unsupported-fidelity diagnostics until exact boolean-result dashed outlines are implemented. Transition-emitted line segments support WPF `Square` caps by extending endpoints by half the pen thickness, `Round` caps by emitting filled circular cap geometry, and `Triangle` caps by emitting filled triangle geometry with the apex one pen radius outward. Shim bitmap image draws and adaptable real WPF `BitmapSource` image draws record native `DrawTexture` commands through the image-source adapter. Shim-compatible glyph runs record native `DrawGlyphRun` commands with the glyph-run transform composed with the active WPF transform. Shim-compatible formatted text records native `DrawText` commands with the active WPF transform. Built-in blur and drop-shadow effects now flow through `IPortableEffectSource` DTOs before transitional property probing, keeping normal source-built effect parameters on a typed path while retaining native ProGPU effect execution. Opacity scopes record native `PushOpacity`/`PopOpacity` commands. Clip scopes record native `PushGeometryClip`/`PopGeometryClip` commands, preserving non-rectangular clip intent. Native opacity-mask scopes carry the active WPF transform in the recorded ProGPU command. Null generated clip, transform, and opacity-mask resources are represented as no-op sink scopes so later pops preserve WPF stack semantics without emitting native rendering state. Reflected Viewport3D visuals record a `DrawExtension` Mesh3D command to render into the cached offscreen target, then a transformed `DrawTexture` command to composite that target into the 2D visual tree. Geometries that cannot produce a path and image sources whose pixels/codecs/color profile cannot yet be adapted still fall back to shim behavior until their managed representation is ported.

Package-mode shim geometries expose native vector path extraction through `ProGPU.Scene.INativePathGeometrySource`, implemented explicitly by the shim `System.Windows.Media.Geometry` base class over its existing `TryGetPathGeometry(...)` implementation. `ProGpuCompositionCommandSink` consumes that interface instead of reflecting for the shim-only `Geometry.Draw(...)` method, so shim fast paths stay typed.

Source-built real WPF geometries now use the signed neutral `ProGPU.Wpf.Interop` contract instead of a public object-shape reader. Real `PresentationCore.Geometry` implements `IPortableGeometryPathSource`, exports `PortableGeometryPath` DTOs for path figures, arcs, transforms, bounds, and combined-geometry operation trees, and `ProGpuCompositionCommandSink` converts those DTOs into `ProGPU.Vector.PathGeometry`. Source-built real WPF `GuidelineSet` follows the same pattern through `IPortableGuidelineSetSource` and `PortableGuidelineSet`, letting dynamic guideline X/Y snapping consume typed arrays instead of reflected `IsFrozen`, `IsDynamic`, `GuidelinesX`, and `GuidelinesY` properties. Generated and object-shaped drawing-context guideline replay should keep that transport single-read: one `TryReadDynamicGuidelineSet(...)` call supplies both the direct `PushGuidelineY1`/`PushGuidelineY2` fast paths and the full-set fallback. Source-built real WPF `Transform` and the ProGPU shim now expose `IPortableTransformMatrixSource`, so the shared resolver can read affine matrix values through `PortableMatrix3x2` before falling back to reflected transform-shaped objects. The sink no longer uses `System.Reflection`, non-public `BindingFlags`, public `GetProperty(...)` geometry reads, or reflected draw invocation for geometry conversion.

The ProGPU shim formatted-text path now keeps WPF-compatible `System.Windows.FontWeight`, `FontStyle`, and `FontStretch` value semantics and copies typeface-derived bold/slanted intent into native `DrawText` command metadata. That keeps reused WPF-shaped managed text calls on the same command-recording path as GDI and glyph-run style simulation instead of adding bridge-side text style compensation.

As of the `ba59fdf` ProGPU submodule update, the production dashed-combined-geometry path no longer has to use operand-boundary outlines when a WebGPU context is available. `ProGpuCompositionCommandSink` resolves the native combined `PathGeometry` through `PathOpGeometrySolver` and dashes the boolean-result boundary; only context-free transition/test fallback keeps the older operand-boundary dash emission and unsupported-fidelity diagnostic. The same bridge conversion now forwards WPF `PathGeometry.FillRule` and every path segment's `IsStroked` flag into the ProGPU vector path ABI before recording native commands.

Rectangular clip scopes intentionally stay on ProGPU's native scissor path. The compositor now transforms all four local clip corners before deriving the conservative screen-space scissor bounds, so rotated or sheared WPF visual clips, scrollable-area clips, and unsupported-geometry rectangular fallbacks do not need managed WPF-side compensating bounds code.

Combined geometry is now part of the ProGPU-owned vector path model for WPF shim users as well as the transition bridge. `ProGPU.Vector.PathGeometry.CreateTransformed(...)` preserves line, quadratic, cubic, and arc segment metadata while baking child transforms into native path-op operands, and shim-level `CombinedGeometry` maps WPF `Union`, `Intersect`, `Xor`, and `Exclude` to ProGPU path-op ids instead of forcing bounds fallback.

Primitive WPF shim geometries now use the same native path representation. `LineGeometry`, `RectangleGeometry`, `EllipseGeometry`, and `GeometryGroup` expose `TryGetPathGeometry(...)`; rectangles and ellipses reuse `ProGPU.Vector.PrimitivePathGeometry`, so ellipse/group clips keep native arc segments and path masks. Shared `ProGPU.Vector.PathGeometry.TryGetBounds(...)` computes ordinary and combined path bounds, including transformed arc bounds after `CreateTransformed(...)`, so shim geometry bounds no longer need duplicate managed arc/bounds code. WPF `PathGeometry.Draw(...)` also splits fill and stroke only when a figure has `IsFilled=false`, excluding those figures from fill atlas commands while leaving the full path available to native stroke commands.

Real WPF `PresentationCore` uses the same direction for non-Windows `PathGeometry` bounds. The assembly source-includes the minimal `ProGPU.Vector` path/arc/dash/transform-metric helper set as internal implementation code, converts parsed WPF path figures into `ProGPU.Vector.PathGeometry`, applies the combined path/world transform through `CreateTransformed(...)`, and queries `TryGetBounds(...)` instead of keeping a WPF-local endpoint-radius arc box. WPF remains the owner of managed path parsing and public geometry objects; ProGPU owns the reusable transformed path/arc bounds math used for layout, clipping, and retained cache sizing.

WPF path fill and stroke metadata is now part of the ProGPU vector ABI. `ProGPU.Vector.PathGeometry.FillRule` is carried into `GpuPathRecord.FillRule`, where the path rasterizer and path-op shaders choose `EvenOdd` or `Nonzero` winding behavior natively. The WPF transition bridge, WPF `PresentationCore` shim, WPF `GeometryGroup`, and WinUI path shim forward their API fill rules into that field. `PathSegment.IsStroked` is preserved from WPF `StreamGeometryContext` and through ProGPU affine transforms, Bezier/arc subdivision, and path-op figure copies; fill compilation still sees every segment, while stroke tessellation skips non-stroked segments and treats them as contour breaks for caps and joins. This keeps WPF-compatible path semantics in ProGPU rather than adding managed contour-rewrite or stroke-filter workarounds in the WPF bridge.

## Managed WPF Reuse Strategy

The migration should move WPF managed code in layers:

1. Keep dependency properties, Freezable, animation clocks, visual tree, layout, and drawing object model managed.
2. Redirect generated `RenderDataDrawingContext` methods from `RenderData.WriteDataRecord(MILCMD, ...)` to an in-assembly sink, route visual render-open through a scoped provider, then bridge that sink through `WpfRenderDataSinkProviderBridge`, an active `ProGpuWpfDrawingFrame`, and ProGPU-backed WPF `DrawingContext` to `IWpfCompositionCommandSink` in the ProGPU lane.
3. Use `WpfCompositionDrawingContext` as the source-level adapter for new ProGPU render targets, and keep `WpfRenderDataBridge` plus `WpfMilRenderDataDecoder` as a typed portable bridge for existing `RenderData` buffers during the transition.
4. Replace DUCE resource creation/update/release with ProGPU resource handles and command references.
5. Replace `HwndTarget`/`HwndSource` on non-Windows with `PortablePresentationSource` plus a Silk.NET-backed ProGPU host while keeping WPF's `PresentationSource` and `CompositionTarget` API shape.
6. Replace native helpers with platform services or pure managed implementations.
7. Fold the ProGPU shim back into the real WPF assemblies once enough native-only seams are abstracted.

The typed bridge is now the product architecture for WPF/ProGPU boundaries. Managed WPF code should expose `RenderData` snapshots, generated render-data sinks, portable visual/resource DTOs, or typed service registrars in assembly; private-field reflection should remain limited to historical harnesses or offline analysis tooling, not product replay.

The reuse rule applies to XAML serialization as well as rendering. `XamlReader`, `XamlWriter`, `ResourceDictionary`, `ResourceKey`, theme-style keys, namescope, resource-expression, binding, template, style-trigger, rich document object graphs, and XAML compiler behavior should remain in the ported WPF managed assemblies. The ProGPU boundary should receive rendered visual/resource intent and native platform events. If the serializer reaches internal WPF concepts such as `SystemResourceKey`, `SystemThemeKey`, default empty runtime-name properties, or rich text default property state, the durable fix is to make the WPF serializer express or suppress those concepts through WPF's existing XAML forms, not to add a ProGPU-side serializer or managed object-graph workaround.

The SDK package lane now treats loose XAML reader/writer parity as a deliverable requirement, not just a source-tree harness detail. The `ProGPU.Wpf.Sdk` smoke must continue to validate `XamlReader` resources/styles/bindings and `XamlWriter` Freezable, system resource-key dictionaries, style dictionary, `BasedOn`, setter, `ControlTemplate`, referenced-library theme `ControlTemplate`, `DataTemplate`, `HierarchicalDataTemplate`, `ItemsPanelTemplate`, `GroupStyle`, `ItemsSource`, trigger, generated-content namescope, group header and items-host panel metadata, live `FrameworkElement` child graphs, live `FlowDocument` rich text graphs, dependency-property value serialization, and template-application round-tripping from SDK-produced artifacts so apps can switch only the project SDK and keep runtime XAML features intact.

The SDK package layout is also part of the architecture contract. `ProGPU.Wpf.Sdk` must remain an `MSBuildSdk` package with root `Sdk/` imports and portable `targets/` assets, not a runtime assembly package. Its package-mode defaults should own WPF markup compilation settings, portable framework-reference suppression, ProGPU/Silk.NET/support package references, automatic non-Windows bootstrap injection, and managed/native runtime asset copying. The external SDK smoke now validates this nupkg shape before building a temporary app so SDK packaging regressions fail at the platform boundary instead of surfacing as app-project changes.

Package-mode SDK validation must not rely on the user's global NuGet cache for mutable `11.0.0-dev` packages or repo toolset SDKs. Repo-local and generated external smoke `NuGet.config` files should use isolated `globalPackagesFolder` locations when restoring from the local artifact feed, and repo-local smoke configs should include the same WPF dotnet feed set needed by Arcade/toolset and pinned transport packages. Fixed-version ProGPU/WPF package refreshes are then actually exercised by the SDK smoke and screenshot probes. The SDK also clears known WPF and ProGPU runtime DLLs from the app output before recopying package assets when mutable `-dev` versions are selected, because MSBuild's normal `SkipUnchangedFiles` optimization can otherwise leave an old `ProGPU.Wpf.dll` or `ProGPU.Scene.dll` beside a freshly restored app. This is part of the SDK deliverable contract because stale packages or stale copied outputs can reproduce obsolete renderer behavior even when the source tree has the correct logical/physical DPI split.

The SDK smoke now treats the loaded ProGPU render-surface API as a validation boundary. Both the repo-local runtime harness and generated external SDK smoke inspect the actual `ProGPU.Wpf.dll` and `ProGPU.Scene.dll` copied beside the SDK-built app and require the host logical client-size properties plus the exact logical-scene/physical-render-target render overload chain from `ProGpuWpfWindowHost.Present(...)` to `ProGpuWpfCompositionTarget.Render(...)` to `ProGPU.Scene.Compositor.RenderScene(...)`. The same package validation requires portable `PresentationSource` logical-size/DPI synchronization and logical-cache DPI reconciliation APIs on the shipped bridge. This keeps the no-source-change SDK deliverable from passing with stale mutable packages that would still draw a WPF logical scene into only the upper-left physical-pixel quadrant on Retina/HiDPI surfaces.

The visible repo-local SDK smoke also validates runtime package identity before showing the window when it runs from the repository output tree. It walks back to `artifacts/packages/Release/NonShipping` and SHA-256 compares the loaded `ProGPU.Wpf`, `ProGPU.Scene`, and `ProGPU.Backend` DLLs against the `lib/net10.0` entries in the local `11.0.0-dev` nupkgs. Direct apphost launches therefore follow the same package-freshness rule as the runtime harness and avoid compensating in WPF layout or compositor coordinates for stale fixed-version package extraction.

Retained WPF replay roots are part of that same logical-coordinate contract. `ProGpuWpfDrawingFrame` and `ProGpuRetainedCompositionCommandSink` must size scene, retained, source-owner, effect, cache, and flat drawing roots in WPF DIPs, while `ProGpuWpfWindowHost` and `ProGPU.Scene.Compositor` use framebuffer pixels only for swapchain configuration, render targets, DPI uniforms, texture allocation, masks, effects, and cached layer backing stores. The retained layer root applies the frame DPI scale after keeping logical bounds, so WPF replay compensates the portable presentation transform without changing WPF layout or owner branch dimensions. A retained branch that uses physical pixels as its logical size can reproduce the macOS Retina upper-left-quadrant SDK smoke rendering even when the compositor logical/physical overload is present.

Nested offscreen rendering is a backend coordinate boundary, not a WPF layout boundary. When the compositor is already rendering a `420x840` DIP scene into an `840x1680` physical swapchain and a WPF retained layer, Skia layer, mask, or native effect needs an intermediate texture, that offscreen texture becomes the authoritative pixel target for scissor, mask allocation, effect uniforms, and `CurrentCanvasPixelWidth/Height` until the pass completes. The outer explicit swapchain size must be restored afterward. This prevents SDK smoke offset regressions without shifting managed WPF visual roots or resizing layout in physical pixels.

GPU resources referenced by deferred drawing commands follow the command-owner lifetime. A caller-provided `DrawingContext` can outlive the `SKCanvas` that recorded save-layer output into it, so command-referenced layer/effect textures must be retained by the `DrawingContext` and released when the context is cleared or converted into a retained picture. Canvas-owned cleanup is reserved for intermediate textures that are no longer referenced by recorded commands. WPF retained effect/cache replay should use the same ownership model so recorded command lists cannot point at disposed ProGPU textures.

Portable WPF layout has the same rule. On non-Windows, `PortablePresentationSource` is the layout owner that corresponds to `HwndSource` for HWND-backed WPF: the ProGPU/Silk.NET host must push the resolved logical client size into the source, and the source must measure/arrange its root visual in DIPs before retained replay reads `RenderSize` or visual content. DPI scale and client size are separate inputs: DPI controls transform/device-scale state, while client size controls WPF layout. Feeding only DPI, or feeding physical framebuffer dimensions as layout size, can leave SDK-smoke content offset or constrained to the wrong quadrant even though the WebGPU swapchain and ProGPU compositor are correct.

The host must also reconcile the final resolved logical client size before WPF layout observes it. Silk.NET/native callbacks can briefly report physical-pixel client sizes, or report no framebuffer size during startup, so `ProGpuWpfWindowHost` compares the resolved size with the cached portable-presentation/source-requested WPF DIP size and the known monitor scale. When the larger dimension is only a monitor/common DPI-scale multiple of the cached DIP value, the DIP value remains the WPF layout size while ProGPU still configures and renders to the physical target. Arbitrary user resizes that are not DPI-scale multiples remain real logical resizes. This keeps startup Retina fixes in the windowing/DPI boundary and avoids compensating through shader, compositor, retained-root, or managed layout offsets.

`BindingGroup` and validation visuals remain managed WPF manager boundaries. The external SDK smoke now compiles and executes group-level validation rules, proposed-value reads, explicit binding source updates, validation error attachment, rejected commits, accepted commits, and a compiled `Validation.ErrorTemplate` that creates and removes an `AdornerLayer` validation adorner from SDK-produced BAML. ProGPU/Silk.NET should render the resulting element/error state and provide native input/render scheduling; it should not maintain a parallel proposed-value table, validation-rule runner, binding-expression model, validation adorner model, or source-update pipeline.

Visual subtree replay currently covers `DrawingVisual` and `UIElement` content backed by `RenderData`, `MilDrawDrawing` for common drawing resources, source-integrated child traversal through `IPortableVisualChildrenSource` with `Children`/protected visual-member fallback for transition shapes, compatible transform/offset/native-primitive-draw/native-geometry-draw/native-geometry-clip/scrollable-area-clip/opacity/opacity-mask/guideline state, supported `BitmapScalingMode=NearestNeighbor`/`LowQuality`/`Linear`/`HighQuality`/`Fant` image-sampling state, supported `EdgeMode=Aliased` vector edge state, supported `TextRenderingMode=Aliased`/`Grayscale`/`ClearType` text antialiasing state, reflected Viewport3D mesh payload compilation, and reflection adaptation for solid brushes, linear and radial gradients with large stop tables, bounded mapping/spread/invertible affine brush-coordinate transforms/color-interpolation methods, radial gradients with separate X/Y radii and gradient origins, pens, matrix/translate/scale/rotate/skew/transform-group affine transforms, line geometry, rectangle geometry, ellipse geometry, geometry groups, combined geometry, reflected path geometry, parseable path geometry, simple glyph runs, bounded `ImageBrush`, `DrawingBrush`, and `VisualBrush` geometry fills with relative/absolute viewports, relative/absolute cropped viewboxes, adaptable affine absolute and relative brush transforms, `AlignmentX`/`AlignmentY`, `Stretch=None`/`Fill`/`Uniform`/`UniformToFill`, and bounded `TileMode=Tile`/`FlipX`/`FlipY`/`FlipXY` replay, and opt-in bitmap source upload for common 32-bit, 24-bit, packed grayscale, indexed palette, 16-bit grayscale/BGR, 48/64-bit integer RGB/RGBA, non-profiled scRGB float, and non-profiled CMYK formats. Visual opacity masks use reflected bounds, render size, actual size, or finite bounds inferred from replayable self or child render-data content, including transformed content records. Reflected drawing groups report partial replay when supported children draw but unsupported siblings remain, so bring-up diagnostics do not hide missing content. Reflected geometry groups preserve their fill rule and bake child path transforms into copied figures during pure-path flattening; mixed groups containing combined geometry are folded into ProGPU union combined-path trees so path children and nested boolean content both survive native command emission. Reflected path geometry preserves figures, fill rule, line/polyline, quadratic/polyquadratic bezier, cubic/polycubic bezier, and arc segment metadata. Reflected combined geometry preserves WPF `Union`, `Intersect`, `Xor`, and `Exclude` as ProGPU combined vector paths using operation ids `2`, `1`, `3`, and `0` respectively; `Exclude` maps to ProGPU difference `A - B`. Geometry-owned transformed arcs, transformed arc clips, and transformed arcs inside flattened geometry groups stay native ProGPU arc segments via the ProGPU affine arc transform helper, falling back to lines only for degenerate arcs. Supported visual `BlurEffect`, `DropShadowEffect`, registered WPF `ShaderEffect` replacement descriptors, and context-bound emulatable legacy `BitmapEffect` descriptors can replay through retained ProGPU effect visuals. Unregistered WPF `ShaderEffect`, non-emulatable bitmap effects, non-context bitmap-effect inputs, cache mode, unrecognized bitmap scaling modes, `ClearTypeHint`, and text hinting mode are counted as unsupported visual state during transition replay until their resource mapping is explicit instead of being silently ignored.

Source-built brush resource adaptation is moving off the reflected fallback one brush family at a time. Real `SolidColorBrush`, `LinearGradientBrush`, and `RadialGradientBrush` plus the ProGPU shim now expose `IPortableBrushSource` through neutral `PortableBrush` DTOs, so normal solid and gradient replay reads color, stops, mapping/spread/color-interpolation state, opacity, endpoints/radii, and brush transforms without property/indexer reflection. The reflected gradient reader remains only as transitional compatibility scaffolding for fake or external WPF-shaped resources that do not yet implement the typed contract.

Package-mode transform adaptation must stay independent of shim-only `System.Windows.Media.Matrix` identity. The reflection resolver now reads WPF-shaped transform values into a neutral affine matrix, the MIL decoder and visual-tree renderer prefer native `Matrix4x4` transform scopes when the sink supports them, and managed `MatrixTransform` objects are created reflectively only for cold compatibility paths. SDK-switched apps therefore load the real WPF transport assemblies without JITting transform metadata that points at the ProGPU shim assembly.

The Viewport3D path is now typed through `IPortableViewport3DSceneSource`/`PortableViewport3DScene`. Source-built WPF owns camera, viewport, light, model, mesh, material, transform, and version export; `WpfViewport3DSceneBridge` creates ProGPU `Viewport3DCompilationPayload` instances without probing WPF-shaped properties. It supports perspective and orthographic projection-camera matrices, mesh positions, indices, normals or generated normals, model transforms, front/back materials, diffuse/specular/material-group colors, and simple directional/ambient light hints. It does not yet implement WPF 3D hit testing, `Viewport2DVisual3D`, texture brushes as mesh materials, animation clocks, camera controller behavior, exact WPF lighting/material semantics, or deeper retained geometry-version invalidation.

Transition invalidation now has a reflection tracker for source objects that expose `Changed`, `Invalidated`, `INotifyPropertyChanged`, `INotifyCollectionChanged`, or common numeric version members such as `Version`, `ChangeVersion`, and `_version`. The tracker follows common visual/resource references such as children, content, drawing collections, brushes, pens, geometries, path figures/segments/points, combined-geometry operands, gradient stops, image sources, glyph runs, transforms, relative brush transforms, visual-brush source visuals, clips, opacity masks, effects, bitmap-effect inputs, shader pixel resources/register fields, cache modes, guideline sets, and Viewport3D camera/model/material/mesh collections. It records dirty source identity for attach, event, property-change, collection-change, and reflected version-poll invalidations so later source-object-to-native-branch mapping can produce dirty rectangles instead of falling back to whole-tree replay. `ProGpuWpfCompositionTarget` attaches this tracker during visual replay and invalidates the ProGPU root visual when the source graph changes. `ProGpuWpfWindowHost` polls `DetectWpfSourceChanges()` before frame-state capture, so version-only source mutations are converted into native retained-root invalidation before an unchanged-frame skip is considered.

Portable `MediaContext` render requests are part of the same dirty-source contract. On non-Windows, `Visual.PropagateFlags(...)` calls the source-aware `MediaContext.PostRender(invalidatedSource)` overload when the portable render service is enabled, and `PortableMediaContextRenderService` delivers that source to `WpfPortableWindowActivation`. The activation bridge marks the source dirty on `ProGpuWpfWindowHost` before requesting a render; if the source maps to an exact retained branch, ProGPU can replay only that branch, and if it is unmapped or unknown the existing retained-root fallback replays the WPF tree. This prevents input/text changes from presenting an unchanged retained layer while still keeping the invalidation decision in managed WPF rather than in app code.

Render requests are coalesced through `IWpfRenderScheduler`. `ProGpuWpfWindowHost` requests a render when the root visual changes, the Silk.NET surface resizes, the target loads, title/client-size/visibility/window state changes, or the tracked WPF source graph invalidates through notifications or version polling. The default host now owns a `DispatcherWpfRenderScheduler` when platform dispatcher/timer services are available; callers can still replace `WpfRenderScheduler` with a custom scheduler, and unavailable platform services fall back to immediate coalescing. Scheduler wakeups are connected back to the Silk.NET host through a dispatcher-thread, non-reentrant `DoRender()` guard and are detached when schedulers are replaced or the host is disposed. In real WPF `PresentationCore`, `MediaContextNotificationWindow` now avoids hidden HWND/user32/MILCore notification-window setup on non-Windows; Windows keeps the original DWM/channel-message behavior. `MediaContext` timing now also avoids non-Windows `kernel32` by using `Stopwatch` as the count source while keeping the existing WPF count/frequency conversion helpers. `MediaSystem` now keeps lifetime bookkeeping but skips MILCore partition and DUCE channel creation on non-Windows, leaving `MediaContext` disconnected until a ProGPU/Silk.NET transport exists. Disconnected portable render scheduling also skips MIL interlocked-presentation entry when no DUCE channel exists, while still posting the portable render wakeup. Real WPF `HwndTarget` remains the Windows HWND-backed target, but its Win32 message registration is guarded so the type can load off Windows and construction fails before session/HWND/MIL initialization. Real WPF `PortableCompositionTarget` now owns roots and device transforms without DUCE channel resources, and `PortablePresentationSource` provides the matching non-HWND `PresentationSource` root/source/render-request boundary. The host-owned `WpfPortablePresentationSourceBridge` attachment APIs and `WpfPortableWindowActivation` bind that real source to the current Silk.NET `ProGpuWpfWindowHost` through typed portable source and activation contracts, keep the WPF window object as the root, derive initial host title/size/window state from `PortableWindowState`, keep live WPF title/client-size, DPI/root/render-request state synchronized, expose native close callbacks back to WPF `Window.Close()` with WPF `Closing` cancellation mirrored to Silk.NET `IWindow.IsClosing`, forward WPF hide/minimize/maximize state to Silk.NET, forward Silk.NET focus changes through typed activation callbacks for `IsActive`/`Activated`/`Deactivated`, route normalized keyboard/text/mouse/wheel payloads into WPF `InputManager`, forward external file-drop payloads through typed drag/drop service callbacks, and let real non-Windows `Application.Run` run the Silk.NET host loop. Basic caret cleanup now guards Win32 caret-blink lookup on non-Windows and takes WPF's existing no-blink path. This is still not full WPF `MediaContext` or windowing: keyboard focus/capture edge cases, dirty-region calculation, portable channel notifications, deeper OS event-loop wake integration, animation ticks, IME/stylus, routed drag/drop, shutdown edge cases, and in-assembly `Visual` change flags still need to be ported.

Package-mode SDK smoke rendering uses fixed mutable `11.0.0-dev` package identities while the port is under active development, so deterministic validation must clear both app outputs and the repo-local NuGet extraction cache before restore. Visible upper-left-only Retina output can come from stale SDK smoke package contents even when the live logical `420x840` WPF surface and physical `840x1680` ProGPU swapchain geometry are correct. The SDK CI gate therefore treats `artifacts/bin`, `artifacts/obj`, and `artifacts/nuget/ProGPU.Wpf.SdkSwitchSmoke` as mutable build products for the smoke projects, while render-coordinate and retained-replay changes remain covered by the headless HiDPI pixel tests.

The visible smoke app should keep failing fast on package identity mismatches until the mutable fixed-version development packages are replaced by immutable versioned artifacts. This keeps screenshot probes meaningful: a direct apphost capture that reaches the window has already loaded the same ProGPU bridge/backend bits present in the current local feed.

Glyph-run adaptation preserves WPF glyph indices, baseline origin, font rendering size, advance widths, optional glyph offsets, and reflected `GlyphTypeface.StyleSimulations` bold/italic flags, then resolves the closest available ProGPU `TtfFont` from a reflected local `GlyphTypeface.FontUri`/font file path when available, by WPF glyph typeface family name when not, or by platform fallback as a last resort. Successfully loaded font files are cached by path so repeated glyph-run replay does not reload the same font data. Once adapted, the composition sink records the run as a native ProGPU `DrawGlyphRun` command carrying the active transform and style-simulation flags.

This glyph path is an intermediate replay bridge. It does not replace WPF text formatting, LineServices, DWrite shaping, bidirectional text handling, font fallback chains, caret stops, or full glyph typeface simulation and fallback identity beyond the current bold/italic simulation flags. The in-tree portable text boundary now source-shares ProGPU's basic one-scalar-to-one-glyph analyzer fallback with cluster maps and metric-derived advances, but it deliberately does not implement OpenType feature shaping, ligatures, contextual substitution, mark positioning, or complex script handling. The real-theme replay now keeps the implicit-style Fluent `CheckBox` visible by classifying private-use icon-font scalars as simple fast text on non-Windows and allowing missing private-use glyphs to use WPF's null-glyph unshaped `GlyphRun` placeholder when Segoe Fluent/MDL2 is unavailable. That keeps the real WPF theme/control tree measurable without entering native `TextFormatterContext.LoCreateContext`, but exact icon fallback is still unresolved. The remaining text concerns still need a deliberate stack decision: route WPF formatted text through ProGPU's text APIs or introduce a cross-platform shaping/line-formatting layer before emitting ProGPU glyph commands.

The root `PresentationCore` and `PresentationFramework` build graphs now succeed on macOS after the SDK/build-tool bring-up changes, the non-Windows `MS.Internal.Text.TextInterface` boundary documented in `progpu-wpf-text-stack.md`, and Windows-only guards around every managed-graph `DirectWriteForwarder.vcxproj` reference in `PresentationCore`, `ReachFramework`, and `PresentationFramework`. Direct `ProGPU.Text` project references from root WPF assemblies are still deferred while the TFM/project graph is split, so focused ProGPU text helpers are source-shared as internal WPF implementation details. This confirms the next in-assembly port boundary: replace the source-shared simple analyzer fallback, remaining CFF subsetting gaps, and LineServices seams with real cross-platform implementations before claiming formatted text fidelity, then move from buildable managed assemblies toward a Silk.NET-backed `CompositionTarget`/windowing path.

Image replay is deliberately explicit because it allocates GPU textures and must respect the active ProGPU context. The low-level reflection resolver uses exact ProGPU shim identity unless an `IWpfImageSourceAdapter` is supplied. The composition target exposes that adapter for replay calls, and the Silk.NET window host enables `WpfBitmapSourceImageAdapter` by default so WPF-shaped retained visuals can draw common bitmap content during bring-up. Full WIC replacement still needs platform codecs, metadata/color-profile policy, caching, invalidation, download state, texture-backed bitmap sources, and lifetime management.

Shader effects should be ProGPU-native rather than managed pixel loops. ProGPU.Scene now includes a `WpfShaderEffect` compositor extension with a WebGPU/WGSL execution contract for WPF-style `c#` constants packed as 32 `vec4<f32>` registers, bounds/texture-size uniforms, source-register metadata, a fixed 16-slot sampler-register bank, transparent fallback textures for unbound samplers, explicit compositor-compatible pipeline layouts, cached native texture bind groups, and cached render pipelines. `WgpuContext` requests and records sampled-texture, sampler, and bind-group limits, and `WpfShaderEffectExtensionPipeline` keeps active masks bound for all-16-register WPF shader effects only when the actual device can bind the extra mask texture/sampler. Devices that cannot bind the additional mask resource skip that draw with a transient backend diagnostic but leave the reusable `WpfShaderEffectParams` valid, so the same WPF effect can render again when the mask scope is removed. Native WPF shader-effect and image-effect pipelines include source alpha mode and active blend mode in their pipeline keys, and WPF shader-effect shader-module keys also include source alpha mode plus a stable shader-source hash because the WGSL fragment wrapper is specialized per alpha convention and mutable native shader replacements must not reuse stale modules under an explicit WPF shader key. This keeps premultiplied offscreen visual sources and WPF/Skia/GDI blend scopes in the backend instead of requiring managed-side pixel workarounds. WPF shader-effect WGSL wrappers branch by source alpha mode: premultiplied sources scale RGB and alpha by opacity/mask coverage, while straight-alpha sources keep straight RGB and scale only alpha/coverage before straight-alpha blending applies coverage once. Image-effect color operations now run in straight color space for premultiplied sources and premultiply output again inside the native image-effect shader path, preserving WPF-style color math without a managed prepass. The ProGPU backend also owns WPF-compatible alpha semantics for general texture, vector/text, image-effect, Skia surface, and GDI bitmap paths: straight-alpha `Src`, `Plus`, and fixed-function-incomplete `DstOver` writes reach premultiplied render targets through native blend or premultiplied shader-entry selection, mask render passes use mask-specific WGSL entry points for `R8Unorm` vector/text/texture targets so computed alpha is stored in the sampled red channel, straight image effects apply opacity once by keeping straight RGB and scaling coverage, straight-alpha texture masks scale coverage once while premultiplied texture masks scale RGB and alpha together in the native texture shader path, CPU-backed `SKSurface` uploads unpremultiplied buffers as premultiplied render-target contents and converts readback to the requested `SKAlphaType`, loaded straight-alpha `System.Drawing.Bitmap` contents are premultiplied before being preserved into GPU draw flushes, solid-color `SKPaint` blend-mode color filters are applied before brush/pen conversion while shader/image color-filter combinations fail explicitly until native filter pipelines exist, and swapchain configuration now falls back to advertised present modes instead of forcing unsupported `Immediate` mode. Shader WGSL can use `wpf_sample_source(uv)` for the reflected WPF implicit input, even when that input is not sampler register 0, or `wpf_sample_register(registerIndex, uv)` for explicit sampler-register inputs. The backend resolves the declared WPF source register before sampler register 0 when selecting primary texture metadata, so source alpha mode and texture-size uniforms match `wpf_sample_source(...)`. The ProGPU backend also has a visual-level `ProGPU.Scene.WpfShaderEffect` descriptor that renders the affected `Visual` into an offscreen texture, binds that visual source to the reflected WPF implicit-input sampler register, and replays the shader through the same native WebGPU extension on the main pass. The WPF bridge can reflect WPF-shaped `BlurEffect` and `DropShadowEffect` objects into ProGPU-native `BlurEffect`/`DropShadowEffect` descriptors, can reflect supported context-bound legacy `BitmapEffect` objects through WPF's modern-effect emulation descriptor without running a managed pixel path, and can reflect WPF-shaped `ShaderEffect` objects into `ProGPU.Scene.WpfShaderEffect` when a native WGSL replacement is registered by effect type, pixel-shader URI, or pixel-shader bytecode hash. `WpfShaderEffectRegistry` is intentionally a native replacement registry, not a CPU shader fallback: it provides the ProGPU shader source and stable shader key while reflected WPF float constant registers, implicit input sampler register, image-backed `ImageBrush` sampler registers, compositor-rendered finite `DrawingBrush`/`VisualBrush` sampler registers, nearest/linear sampling mode, and shader padding are copied into the ProGPU descriptor. The Silk.NET host now replays `WpfRootVisual` through a retained ProGPU scene layer. `ProGpuRetainedCompositionCommandSink` creates bounded retained drawing visuals for supported visual-effect scopes, localizes effect content into the inferred bounds, and lets ProGPU's native `Visual.Effect` path perform the offscreen blur/drop-shadow/shader work. Reflected `DrawingGroup` replay also uses this retained effect-scope path for supported group `Effect` descriptors and context-bound emulatable bitmap effects, wrapping child drawing replay without managed pixel processing. The WPF bridge's `WpfShaderEffectSamplerTextureCache` renders finite replayable shader sampler brushes into cached ProGPU textures through the same `DrawingBrush`/`VisualBrush` replay path used for geometry fills, and clears that cache when the retained WPF root is rebuilt. The direct flat replay path still reports visual effects as unsupported because it has no retained visual boundary. The remaining WPF work is non-emulatable bitmap effects, non-context `BitmapEffectInput`, advanced/unbounded brush shader sampler inputs, other non-image sampler texture inputs, and translation/import for legacy Direct3D pixel-shader bytecode, because WebGPU cannot execute that bytecode directly.

Mutable effect invalidation is also native scene state. `ProGPU.Scene.EffectBase` keeps weak owner links to visuals that reference an effect, and effect property changes invalidate those owners so normal parent dirty propagation refreshes cached layers and retained effect textures. The WPF bridge should pass WPF effect intent into ProGPU descriptors and should not add a separate effect-polling or managed replay invalidation layer for this case.

WPF shader-effect failure state is native backend state, but it must be keyed by the shader identity that produced the failure. Retained `WpfShaderEffect` records the shader key/source hash for a latched compile/pipeline failure and clears that failure when the caller replaces the shader source or key, allowing corrected WPF shader effects to recompile without app-side state resets. ShaderToy compatibility follows the same rule: GLSL builtin return-type fixes such as vectorized `mod(...)` resolution belong in ProGPU's transpiler so WPF-facing shader surfaces do not rewrite expressions before handing them to the native path.

Advanced blend modes that fixed-function WebGPU cannot express correctly for straight source RGB stay native by selecting shader entry-point variants rather than by rewriting WPF commands. `DstOver`, `Screen`, and `Multiply` now use premultiplied fragment entries for vector, text, and straight-alpha texture draws before the backend blend factors run, while already-premultiplied textures keep the normal entry point. This preserves WPF/Skia-style semi-transparent blend behavior and avoids managed bridge-side shader or color premultiplication passes.

Generic ProGPU texture construction is treated as an upload-oriented API and defaults to straight-alpha RGBA semantics for existing `WritePixels(...)` callers. Textures that are rendered into or that store WPF PBgra/render-target contents opt into `GpuTextureAlphaMode.Premultiplied` at allocation, including Skia surfaces, GDI bitmaps, WPF `WriteableBitmap`, host offscreen targets, retained layers, and effect scratch textures. This keeps alpha convention at the backend resource boundary rather than requiring WPF bridge-side pixel rewrites.

Generic ProGPU texture readback is also a backend API contract. `GpuTexture.ReadPixels(...)`, framework CPU-framebuffer fallbacks, DirectX/SciChart texture read maps, and Skia/backend snapshots should share `ProGPU.Backend.GpuTextureReadbackBuffer` for texture-to-buffer copies, WebGPU row-pitch alignment, mip and depth/array-layer copy layout, depth-aspect selection, map polling, `finally` unmap, and ordered backend buffer disposal. Framework adapters should not add their own staging-buffer loops when the backend helper can be extended for the needed subresource or async/pool behavior.

Generic ProGPU buffer readback follows the same ownership rule. `GpuBuffer.ReadBytes(...)` should be the shared path for DirectX staging-buffer reads, compute result reads, SciChart adapter readback, and framework diagnostics, with map polling routed through `WgpuContext.PollDevice(...)` and temporary readback buffers queued through the backend disposal queue. Adapters should not add local `wgpuDevicePoll` imports or direct WebGPU buffer destroy/release calls; if a workload needs async, pooled, or paged readback, extend the backend contract so WPF, WinUI, Avalonia, DirectX, and Skia-compatible surfaces keep one ordered resource-lifetime model.

Contextless `GpuTexture` instances are not bindable runtime resources. The WPF bridge may accept pointerless/contextless fake textures for command-recording tests so image, shader-sampler, and bitmap-scaling paths can be verified without creating a WebGPU device, but ProGPU's compositor must null-check the texture context and require the active compositor context plus non-null texture/view handles before creating bind groups. Real WPF bitmap upload/adaptation still uses per-`WgpuContext` textures and rejects foreign or disposed resources before recording bindable draws.

Rectangular texture clipping is a compositor optimization boundary, not a WPF control workaround. ProGPU's shared clipped-quad path should trim axis-aligned texture, cached-layer, image-effect, shader-effect, and third-party control surfaces while preserving source UVs, including mirrored negative-scale transforms. True rotated or sheared quads may still rely on scissor/mask clipping, but simple mirrored WPF/Xceed cell, image, or layer surfaces should not keep broad overdraw just because the transform flips an axis.

GDI and Skia API compatibility should continue to be normalized in the ProGPU shim/backend layer before WPF bridge code compensates. `System.Drawing.Graphics` now scales stroke thickness under world transforms for line, primitive, and path strokes before recording native ProGPU pens. Skia opaque bitmap uploads now normalize alpha bytes to 255 at `SKImage.FromBitmap(...)`, because Skia treats those alpha bytes as ignored while ProGPU textures still carry concrete alpha. CPU-backed `SKSurface` row strides are validated before texture allocation and reused for upload/writeback, so undersized caller buffers fail at the shim API boundary instead of being worked around in WPF interop code. Two-point conical gradients now have a ProGPU-native brush type and WGSL sampler that solves the moving-circle gradient parameter per fragment, so Skia focal/conical gradients can stay on the full GPU path instead of falling back to wrong radial output or managed pixel work. Wrapped backend render targets now carry `GRSurfaceOrigin` into `SKSurface`, and `BottomLeft` targets render through a GPU-side root y-flip during flush so Skia's top-left canvas coordinates land in the correct bottom-left-oriented backend texture without a CPU row-copy workaround. ProGPU compositor render entries now scope the thread-static `WgpuContext.Current` to the active compositor context, and deferred Skia-compatible `SKCanvas.DrawImage(...)` retention now uses that active target context before falling back to the source image context, rejecting cross-context images before recording rather than letting a target command stream retain a texture owned by another WebGPU device. GPU line/scatter buffers track their owning context so render-thread uploads and bind-group cleanup do not depend on the initialization thread. Cached visual layer textures are now valid only for their owning `WgpuContext`, and the compositor releases stale layer textures when their owner visual leaves the active tree, disables layer caching, becomes hidden, points at a different texture, or already holds a disposed texture. Cached texture/mask bind groups, chart line/scatter series bind groups, cached layer textures, and explicitly disposed `GpuBuffer` handles are queued for `WgpuContext` cleanup and released before texture views/textures or context teardown, keeping sampler, buffer, and layer texture lifetime in the backend's ordered render-thread disposal path. `SKSurface.Flush()` also releases command-retained image resources and canvas-owned `SaveLayer` textures from a failure-safe cleanup path after a flush attempt, keeping long-lived Skia-compatible surfaces from retaining one GPU texture per layer per frame even when `RenderOffscreen(...)` or readback fails.

Shader/effect extension teardown follows that same backend-owned lifetime rule. Image-effect and ShaderToy extension bind groups, bind-group layouts, and pipeline layouts are queued through the owning `WgpuContext` disposal queues instead of releasing WebGPU handles directly from UI-side or compositor disposal paths, while uniform buffers use the queued `GpuBuffer.Dispose()` path. WPF shader effects, ShaderToy experiments, Skia filters, and retained effect/layer hosts should therefore rely on ProGPU's ordered `WaitIdle()`/cleanup boundary rather than adding managed WPF bridge workarounds for in-flight WebGPU resources.

`System.Drawing.Graphics.DrawImage(...)` interpolation is also a ProGPU compatibility-boundary responsibility. The shim maps `Graphics.InterpolationMode` into the native texture sampler (`NearestNeighbor` to nearest sampling, bicubic modes to cubic sampling, and the remaining GDI+ modes to linear sampling) when recording `DrawTexture`, so WPF/GDI-compatible image draws can keep their managed API shape while ProGPU owns full-speed sampler selection.

Bitmap image sampling is now part of the transition visual-state bridge. Reflected `BitmapScalingMode=NearestNeighbor` pushes a scoped nearest-neighbor texture-sampling mode into `ProGpuCompositionCommandSink`; `LowQuality`, `Linear`, `Unspecified`, `Default`, and `Auto` use linear sampling, matching WPF's native aliasing of `LowQuality` and `Linear` to the same interpolation mode; and `HighQuality`/`Fant` use shader-side cubic texture sampling. The same supported modes are replayed for WPF-shaped `DrawingGroup.BitmapScalingMode`; unknown bitmap-scaling values report partial replay when supported children still draw. Reflected visual and drawing-group `EdgeMode=Aliased` pushes a scoped vector edge state into `ProGpuCompositionCommandSink`; native ProGPU vector commands carry `RenderCommand.IsEdgeAliased`, the compositor encodes it into the existing `ShapeType` vertex channel, and the vector shader thresholds primitive, stroke, curve, and path-atlas coverage instead of smoothing it. Reflected visual and drawing-group `TextRenderingMode=Aliased`/`Grayscale`/`ClearType` pushes scoped text antialiasing state into `ProGpuCompositionCommandSink`; native ProGPU text commands carry `RenderCommand.TextRenderingMode`, the compositor encodes the mode into the existing text flags channel while preserving the `IsTextAliased` compatibility property, and the text shader thresholds glyph atlas alpha for aliased text, leaves grayscale text on the current smoothed glyph path, and renders ClearType text with RGB subpixel atlas samples. The first tile-brush transitions are intentionally bounded. WPF-shaped `GeometryDrawing` fills and source-level object-sink rectangle/geometry fills can replay `ImageBrush`, `DrawingBrush`, and `VisualBrush` instances when the brush uses relative or absolute viewport units, relative or absolute viewbox units, `TileMode=None`, bounded `TileMode=Tile`, bounded `FlipX`, bounded `FlipY`, or bounded `FlipXY`, `Stretch=None`, `Stretch=Fill`, `Stretch=Uniform`, or `Stretch=UniformToFill`, `AlignmentX=Left`/`Center`/`Right`, `AlignmentY=Top`/`Center`/`Bottom`, and an absent, identity, or adaptable affine `Transform`/`RelativeTransform`. Relative transforms are converted through the finite filled geometry bounds before replay. Tiled paths require finite fill geometry and cap replay expansion. ImageBrush non-full viewboxes are emitted through `IWpfCompositionCommandSink.DrawImage(..., sourceRectangle)` and ProGPU `DrawTexture.SrcRect` when the adapted image exposes pixel dimensions. DrawingBrush and VisualBrush non-full viewboxes are handled by mapping the selected source bounds into the brush viewport and pushing a transformed source-space clip before nested drawing or visual replay. Non-fill stretch aligns source content inside each tile; oversized `UniformToFill` and source-sized `None` content is clipped to the tile before replay. Flip tiling mirrors alternating tile columns and/or rows by emitting destination-space mirror transforms. All three paths clip to the adapted fill geometry and preserve brush opacity. Non-affine or unreadable transform types and advanced visual-brush cases remain unsupported and are counted as partial unsupported content when a supported stroke, nested drawing subset, or visual subtree subset can still be replayed.

Visual hit testing is also a manager boundary. ProGPU bounds-query results now carry `GpuHitTestIntersectionDetail`, so axis-aligned bounds/rect candidates can report `FullyInside`, `FullyContains`, or `Intersects`, and the shader now runs precise rectangle-region checks for axis-aligned rounded-rectangle fill/stroke, ellipse fill/stroke, cached line-stroke, and cached path fill/stroke candidates before recording them. Ellipse-region query results reuse the same detail channel for simple rectangle fill/bounds primitives and reject query-AABB corner false positives, rounded-rectangle corner false positives, rectangle-stroke interior holes, cached line-stroke broad-bounds false positives, cached path-fill hole false positives, and cached path-stroke broad-bounds false positives before they reach WPF callbacks. If a GPU cache exists and reports no owner, these overrides handle the miss and prevent the CPU drawing-content walk; only startup/no-cache and non-WPF-object cases fall back to the existing WPF path. Remaining conservative framework areas are exact `IntersectionDetail` for arbitrary non-rectangular geometry-region callbacks, portable source detection of simple WPF query geometries, and broader combined/path-op stress cases; these should use shader-side region/stroke/fill intersection on top of the GPU candidate list rather than expanding managed WPF into a second geometry engine.

Path hit-test helper data should be shared with rendering rather than rebuilt by a second managed geometry pipeline. `PathAtlas` owns a bounded content-hash cache of compiled `GpuPathRecord`/`GpuPathSegment` payloads, reuses that payload for atlas rasterization, and supplies it to `GpuRenderCommandHitTestCacheBuilder` during the same frame's render-command compilation. GPU hit-test query submission is also a hot input path. All-hit point, bounds, and ellipse-region queries should reuse the frame's `GpuHitTestDeviceIndex` buffers and clear their result-list upload through stack/span or pooled storage instead of allocating a managed `GpuHitTestResult[]` per mouse move or geometry callback. The WPF owner-resolution bridge follows the same rule: bounded point, bounds, and ellipse owner/candidate spans use stack storage for the common case and pooled `GpuHitTestResult` buffers for larger or retry queries, then resolve owners from those spans without fresh result arrays. If real workloads exceed the bounded result list, the next step should be a paged or streaming GPU result path, not a CPU drawing-content fallback.

Portable visual state is expensive enough to treat as replay-pass data. SciChart native runtime discovery is also part of the `ProGPU.DirectX` compatibility boundary. `ProGpuDirectXNativeDependencyInspector` reflects loaded managed assemblies for `[DllImport]` declarations and scans assembly string metadata for dynamic module names without loading those native binaries. SciChart native compatibility classification also belongs in ProGPU. `ProGpuDirectXNativeCompatibilityPlanner` groups detected modules into ProGPU native facades, host OS Win32 abstractions, managed assembly hints, and unknowns. This keeps Direct3D/DXGI/D3DCompiler work, SciChart licensing/native-engine work, and local OS API replacement work visible as separate backend tasks instead of forcing the WPF sample or managed port layer to guess what a missing `.dll` string means.

SciChart native module resolution is now a ProGPU-owned compatibility hook, not an app workaround. `ProGpuDirectXNativeResolver` installs per-assembly `NativeLibrary.SetDllImportResolver` callbacks, uses the compatibility plan to decide which modules may be handled by a ProGPU native facade, and returns zero when no facade library is configured or loadable. The WPF SciChart Showcase installs that resolver before `SciChartSurface.SetRuntimeLicenseKey(...)` and reports resolver attempts in validation/fallback output, but it must not hide missing proprietary entry points behind managed WPF fallbacks. Future native work should provide the actual licensing, Visual Xccelerator, Direct3D, DXGI, D3DCompiler, and narrow Win32/OS facade exports behind `PROGPU_DIRECTX_NATIVE_FACADE_PATH` or a packaged equivalent.

SciChart native ABI planning also belongs in ProGPU. `ProGpuDirectXNativeAbiPlanner` turns reflected `[DllImport]` metadata into module/export requirements with calling convention, charset, set-last-error, exact-spelling, and import-owner evidence, while preserving string-only dynamic module hints separately. The ProGPU native facade should implement reflected exports first because they are authoritative managed call sites; dynamic Visual Xccelerator module hints require runtime probing, vendor API mapping, or binary export inspection before adding stub exports. WPF sample code may print this plan, but it should not own or hand-maintain the ABI list.

The ABI plan must include managed signatures. Native facade work needs return and parameter metadata to generate correct NativeAOT/C exports, to decide which Win32 calls can be host-abstraction shims, and to identify unsafe proprietary entry points that require runtime probing. `ProGpuDirectXNativeDependencyInspector` now records managed P/Invoke signatures and `ProGpuDirectXNativeAbiPlanner` exposes them per export; WPF should consume that report for diagnostics only.

Native facade source scaffolding is a ProGPU responsibility too. `ProGpuDirectXNativeFacadeSourceEmitter` can turn the reflected ABI plan into NativeAOT `UnmanagedCallersOnly` stub source for exports whose signatures map to unmanaged parameter and return types. The generated stubs are only scaffolding until individual exports are wired to real ProGPU DirectX, SciChart licensing/native-engine, or host OS implementations, but keeping the generator in ProGPU avoids a hand-maintained WPF-side export list.

The minimal DirectX native-facade deliverable is a build artifact handoff, not full proprietary runtime emulation. `ProGpuDirectXNativeFacadeProjectEmitter` packages the generated export source into a NativeAOT shared-library project scaffold so future work can publish one facade library and replace default stubs export-by-export. Until those stubs are replaced with real Direct3D/DXGI/D3DCompiler, host OS, and vendor native-engine implementations, WPF samples should report the facade boundary and return to broader managed WPF portability work rather than adding managed SciChart workarounds.

SciChart native dependency extraction is a sample/startup integration concern, not the durable runtime compatibility layer. The real-package Showcase follows SciChart's documented `SciChart.Core.NativeDllLoader.DependenciesPathRoot` hook and sets it to a writable path before license setup so extraction failures are explicit. That does not replace the ProGPU native facade; once extraction succeeds on macOS, SciChart still expects Windows/DirectX/native-engine exports that must be supplied by `ProGPU.DirectX` and the packaged native ABI facade.

SciChart/DirectX resource lifetimes must extend through native command submission. The Showcase shaped-heatmap path records GPU commands that reference Float32 height buffers and gradient textures, then submits them on `Flush()`. Adapter code must therefore keep those DirectX resources alive until after flush or explicit command-list disposal; disposing them when a helper method returns leaves dead SRV handles in the binding snapshot. ProGPU.DirectX now reports the exact cbuffer/SRV/sampler bindings when a pipeline-compatible bind group cannot be created, so future proprietary SciChart adapter failures should be diagnosed at the DirectX resource boundary rather than hidden by managed WPF bitmap fallbacks.

DirectX alpha and input-layout compatibility are backend API contracts. Direct3D `R8G8B8A8Unorm` and `B8G8R8A8Unorm` texture contents are treated as straight RGBA by default because clears and uploads carry unpremultiplied channel values; WPF, SciChart, or SharpDX adapters should not compensate by premultiplying in managed code unless the caller has opted into a separate premultiplied resource contract. DirectX input-layout formats also fail closed when WebGPU has no shape-preserving vertex equivalent, so scalar formats such as `R8Unorm` and `R16Float` remain valid texture/staging formats but are rejected as vertex attributes rather than widened to two-component WebGPU formats with invalid strides.

DirectX CPU access flags are part of native resource allocation, not a managed adapter hint. `CpuAccess=Read` must allocate textures with backend copy-source capability and `CpuAccess=Write` must allocate copy-destination capability, even when the DirectX usage flags omit redundant copy bits. This matches Direct3D-style staging/readback contracts and keeps SciChart/SharpDX adapters from mutating descriptors only to satisfy WebGPU usage validation.

HLSL shader compatibility should be proven by native readback before being advertised as supported. Vector-valued HLSL conditional expressions now lower to WGSL `select(...)` with explicit vector boolean masks, which keeps SciChart-style palette/material branches inside backend shader execution. Raw WGSL `front_facing` remains disabled because declaring that builtin currently produces black output on the active backend, but HLSL text shaders using `SV_IsFrontFace` now have a ProGPU-native emulation path: `ProGPU.DirectX` compiles constant front/back pixel shader variants and lowers one logical Direct3D triangle draw into cull-selected WebGPU passes, including `UInt16` indexed `DrawIndexed` submissions. This keeps the material branch on the GPU and avoids managed WPF workarounds while preserving the backend capability flag for the real builtin. No-cull blended front-facing pipelines remain fail-closed with an explicit diagnostic until an order-preserving native strategy exists; culled blended pipelines can still use the single-sided emulation path.

DirectX draw resource lifetimes are owned by the backend render pass. GPU-backed draws may create transient bind groups from the active native pipeline layout, including one bind group per shader-variant pass for `SV_IsFrontFace` emulation. Those handles must stay alive until `RenderPassEncoderEnd` and command-buffer submission/release have completed; helper boundaries inside `ProGPU.DirectX` must not release them early just because a logical draw pass has returned.

SciChart text labels follow the same backend ownership rule. The DirectX shim records text/font/style/alignment/clip metadata for adapter mapping, then reuses `ProGPU.Text` font discovery and `ProGPU.Scene.Compositor` text rendering into the active SciChart render target when a GPU-backed device is available. This keeps axis labels, annotations, and chart overlays on the same native render-target path as chart geometry and avoids a WPF-managed label overlay that would diverge from SciChart's DirectX ordering, clipping, and antialiasing behavior. The bridge flushes pending DirectX GPU commands before native text composition so Direct3D-style command order remains explicit.

Small third-party Win32 probes should be handled at the SDK/platform boundary until the corresponding managed WPF or package code is ported to explicit abstractions. `ProGPU.Wpf.Sdk` now supplies a non-Windows `kernel32.dll`/`user32.dll` compatibility shim for benign identity, focus, hook, and rectangle probes used by WPF Toolkit/AvalonDock. This is intentionally narrow: it is not a replacement for WPF's full Win32 subsystem, and APIs that affect real native state should continue moving behind Silk.NET/ProGPU platform services or OS-specific abstractions.

The portable text formatter still has a transitional managed fallback for simple text, including collapsed/truncated simple lines. Non-Windows `SimpleTextLine.Collapse(...)` must not instantiate `FullTextLine` while LineServices is native-only, because third-party templates frequently use text trimming and would otherwise load `PresentationNative_cor3.dll`. The fallback preserves app startup and common control templates, but full fidelity still belongs in the planned ProGPU-backed or cross-platform shaping/line-formatting layer.

Default-discovered SDK resources are an SDK/MSBuild and managed WPF loading boundary. Image and cursor files under ordinary project folders should become WPF `Resource` items without explicit project entries, and BAML/pack URI resolution should create normal `BitmapSource`, `ImageBrush`, or `Cursor` instances before ProGPU sees rendering or cursor-service state. The current non-Windows custom cursor constructor deliberately falls back to a stock WPF cursor object after the resource stream is resolved; native `.cur`/`.ani` decoding and platform cursor presentation should be added behind the cursor service, not by requiring app-side project item changes or renderer-specific cursor APIs.

Viewport clipping is a WPF layout/rendering boundary. Controls such as `ScrollContentPresenter`, `DataGridColumnHeadersPresenter`, and third-party panel templates can produce clip rectangles through protected layout-clip APIs even when the public `UIElement.Clip` property is null. The transition renderer therefore prefers materialized `VisualClip`, then source-integrated `IPortableVisualLayoutStateSource` layout clips from `FrameworkElement`, intersects them with any explicit clip, and lowers rectangular results into ProGPU native clip scopes. Transitional `GetLayoutClipInternal()` probing remains only for non-integrated compatibility shapes. Toolkit/AvalonDock and large WPF `DataGrid` clipping should be fixed in that bridge/native scissor path, not by changing sample XAML or duplicating control scroll logic.

Preview SDK release validation is part of the architecture boundary too. The custom SDK must prove normal WPF app migration from package artifacts, so `eng/progpu-wpf-sdk-ci.sh` validates package-mode SDK switching, real WPF XAML/Application.Run/theme startup, no-source-change external apps, Hello/Showcase live host input and resize, free Toolkit/AvalonDock live behavior, paid Xceed when licensed or forced, SciChart Showcase DirectX-shim smoke, and the graph guard in one lane. A preview package audit then checks the produced nupkgs for SDK MSBuild assets, README metadata, WPF ref/lib transport assemblies, and required ProGPU/Silk/Avalonia dependency metadata before app smokes begin; a manifest step writes package sizes plus SHA-256 hashes; and a release-bundle step archives the manifest with the exact preview nupkg set for handoff. The public package and release-bundle brand is `LibreWPF`, while source and runtime identities stay stable. `LibreWPF.Transport` carries the managed WPF transport payload, `LibreWPF.ProGPU` carries `ProGPU.Wpf.dll`, `LibreWPF.Interop` carries `ProGPU.Wpf.Interop.dll`, and `LibreWPF.Sdk` exposes the no-source-change MSBuild SDK. This keeps NuGet IDs, README headings, SDK examples, workflow names, and preview bundle files legally distinct without renaming source projects, namespaces, target files, or assemblies used by the port.

Retained invalidation snapshot ownership is split by lifetime. The tracker owns stable visual-child topology arrays only in its retained baseline snapshots captured during subscription/refresh, while normal `DetectVersionChanges(...)` polling streams current `IPortableVisualChildrenSource` children directly into comparison and dependency traversal. This avoids rebuilding a full current child-snapshot dictionary for every version probe on large Xceed/AvalonDock/DataGrid trees, preserves typed source-built WPF child enumeration, and keeps removed-source detection through a lightweight current-source set. Pooled arrays must not escape into retained snapshots; new performance work should either stream live topology or allocate only for tracker-owned baseline state.

Retained invalidation subscription refresh should store unsubscribe handles in typed records instead of closure-wrapped actions. Portable invalidation sources that return `IDisposable` handles can be disposed through a direct helper, while event callback unsubscribe actions stay supported through the same exception-tolerant path. This keeps large Xceed/AvalonDock/DataGrid retained dependency graphs from allocating an extra lambda per subscription every time the graph refreshes.

Portable popups are a platform-host contract, not a managed control rewrite. `PresentationFramework.Popup` keeps WPF placement, ownership, `PopupRoot`, `ContextMenu`, `ToolTip`, menu, dropdown, and third-party control semantics, but non-Windows lifetime/position/size/show/hide/hit-testability flows through the typed `IPortablePopupServiceRegistrar` in `ProGPU.Wpf.Interop`. `ProGPU.Wpf` creates/binds popup `PortablePresentationSource` instances, renders each visible popup as a translated retained ProGPU overlay branch above the owner tree, and routes topmost popup input to the popup presentation source before the owner window. WPF-side changes must stay at that service seam; native z-order, GPU hit-test cache use, source-level input, and future transparency/monitor policy belong in ProGPU/Silk.NET.

## Win32 Abstraction Strategy

Win32 usage should be split into three groups:

- Rendering/windowing: move to Silk.NET and ProGPU.
- OS services: introduce local platform abstractions for clipboard, file dialogs, input, window events, monitor/DPI, cursor, drag/drop, dispatcher posting, timers, activation, and MediaContext/channel wakeups. Simple URI/file launching is routed through the cross-platform `ProcessWpfLauncher`; ProGPU host text clipboard access is available through `ProcessWpfClipboard`, and real WPF public `Clipboard` now has a non-Windows `PortableClipboardService` fallback that keeps WPF `IDataObject`/format semantics before the process-backed OS adapter is wired in; file open/save/folder picking is routed through `ProcessWpfFileDialogService`, and real WPF public file-dialog APIs now use `PortableFileDialogService` to enter that platform service before HWND/COM dialog creation on non-Windows; low-level keyboard/text/mouse/wheel input is routed through `SilkNetWpfInputService` and reaches explicit portable top-level input handlers or real WPF's internal `PortableInputEventArgs` handoff through `WpfPortableWindowActivation`; real WPF `InputManager` creates portable keyboard/mouse devices on non-Windows, skips the Windows STA construction gate outside Windows, and now promotes portable raw keyboard/text/mouse/wheel reports into routed WPF input events including the first capture/release, `ButtonBase.Click`, and `MouseWheel` activation over `PortablePresentationSource`; real WPF `QueryCursor`/`IMouseInputProvider.SetCursor(...)` requests on `PortablePresentationSource` are forwarded through the ProGPU host bridge into `SilkNetWpfCursorService`; dispatcher-style callback posting is routed through `QueuedWpfDispatcherService`; render-priority frame scheduling is routed through `DispatcherWpfRenderScheduler`; event-driven native-loop wakeups are routed through Silk.NET `IWindow.ContinueEvents()` when dispatcher/render work cannot be processed immediately on the owner thread; file-drop payloads are routed through `SilkNetWpfDragDropService`; focus-derived activation/deactivation and external file drops are routed through `SilkNetWpfWindowEventService`; monitor bounds, primary identity, and DPI scale are routed through `SilkNetWpfMonitorService`; one-shot/repeating timers are routed through `ThreadPoolWpfTimerService`; non-Windows `MediaContext` clock reads use `Stopwatch`; non-Windows `MediaSystem` startup/shutdown skips MILCore partition and DUCE transport work while preserving lifetime bookkeeping; non-Windows `HwndTarget` type loading skips Win32 message registration and construction fails fast; non-Windows stylus/touch probing is disabled until a portable tablet/input abstraction exists; and non-Windows `MediaContextNotificationWindow` currently no-ops the Windows hidden-HWND DUCE notification hook while the portable ProGPU/Silk.NET channel notification source is still pending.
- Windows-only compatibility: retain a Windows implementation behind the same abstraction where behavior cannot be portable.

No new direct Win32 calls should be added to the ProGPU lane.

## Portable modal windows and native input leases

Modal policy remains managed-framework state. Source-built WPF owns `Window.ShowDialog()`, `_showingAsDialog`, `DialogResult`, owner collections, closing cancellation, and closed-event sequencing. On the portable path it invokes the already-registered typed window-activation `Run` callback for the dialog host while modal state is active; this preserves synchronous WPF API behavior even though portable dispatcher frames are intentionally bounded and ProGPU/Silk.NET owns native event pumping. LibreWinForms maps `Form.ShowDialog(IWin32Window)` onto that WPF contract and resolves non-Form owners through typed `HwndSource.FromHwnd(...)` state, never by reflecting owner objects or passing a synthetic handle to Win32.

Each native window host owns at most one Silk input context lease. Composition-target initialization is treated as a transaction: reentrant initialization fails closed, close/dispose state is checked before and between target/platform-service setup stages, and a target or input subscription created during reentrant shutdown is disposed before it can become host state. `DoEvents()` must stop after an initialization-time close before attempting target creation. Silk input-context construction also has failure cleanup. Do not work around duplicate contexts by swallowing Silk exceptions or globally sharing input devices between unrelated windows; unexpected event-loop failures must remain visible.

## Portable WinForms designer hosts

Managed designer container semantics belong in LibreWinForms, not in SharpDevelop or ProGPU. The portable `IDesignerLoaderHost` should reuse upstream WinForms's `DesignerHost : Container` model: the host owns its components, creates design-mode sites, and makes typed host services available through `IComponent.Site`. Site-local `IServiceContainer` and `IDictionaryService` state, serialization-name synchronization, component rename notification, and deterministic site-service disposal remain managed framework responsibilities. This lets standard property descriptors, designer loaders, selection services, serialization managers, and third-party designers operate normally without private-field scans or nested-container reflection bootstraps.

ProGPU remains responsible for rendering/composition of the hosted control tree, while LibreWPF `WindowsFormsIntegration` owns the typed WPF host boundary. SharpDevelop should only consume standard `System.ComponentModel.Design` and WinForms contracts. Validation hooks must reacquire a stable current designer host after asynchronous view activation; mutating a disposed generation and flushing a replacement generation is a test race, not a reason to change framework serialization.

Application-wide WPF state is dispatcher-affine. Portable worker-thread windows, including WinForms wait dialogs, must compare their dispatcher identity with `Application.Dispatcher` before querying `Application.MainWindow`. A different-dispatcher window is definitively not the application main window and should not marshal or reflect through the property merely to decide native show policy.
